## 0. 一句话结论

**【业界共识】** 国内 AI 短剧/漫剧圈已经把"一致性"从"提示词技巧"升级成了**资产管理问题**：
**资产图必须先于分镜存在并锁定，分镜只做 @引用，不重新描述人。** 这句话在至少四套独立来源里被几乎同义地表述：

| 来源 | 原话 |
|---|---|
| 漫剧老李 `short-drama-director` skill（社群规则库） | "**核心理念：资产图先于分镜。** 角色/场景/道具在 P2 数字资产包阶段完成**出图并锁定**（非文字描述），成为《资产图册》唯一权威事实来源"；"**'名字+装扮'不是资产**……资产 = 可直接投喂模型的资产参考图" |
| ai-comic-studio（开源漫剧工坊，Next.js） | 流水线：`角色提取 → 角色四视图 → 智能分镜 → 首尾帧生成 → 视频`；数据模型里 `Character（视觉描述、9 维音色描述、定妆图/音频资产）` 与 `StoryboardVersion / Shot` 分层 |
| zenstory-ai `drama-skills` | "三视图只解决'这个人长什么样'，解决不了'这一镜他穿什么、拿什么、看向哪'"；只有被检查过的 `REF-*` 图才能进视频提示词参考槽 |
| AntonHu `ai-drama` | 工作流：`剧本 → scene-design 出场景概念图 → character-design 出角色设定图 → storyboard`；"分镜中通过 `@图片` 引用场景与角色资产，确保成片视觉一致" |

**所以我给的第 1 号结论是：资产库不是"人物角色卡的集合"，而是"可投喂的图 + 一份引用台账"。文字卡只是索引。**

### 0.1 但先读这一条：本报告的证据必须分两层看

独立核查得出一条**影响整份报告可信度分层**的负面结论：

> **在本次全部检索中，没有任何一部国内在播 AI 短剧/漫剧的剧集主创，公开说过自己用了「三视图 / LoRA / ControlNet / 固定 seed / 色卡资产」这些词。**
> 这些术语**只出现在教程、开源 skill 仓库、工具方教程与培训机构内容**里；**项目复盘里出现的实际是**：**"种子图"（人设图/场景图/道具图）、垫图、局部重绘、参考图、角色信息 + 图片、动态分镜、跨集位置预对齐、统一镜头风格、3D 资产复用**。

| 层 | 内容 | 证据强度 | 代表来源 |
|---|---|---|---|
| **A. 剧集主创一手层** | 种子图（人设图/场景图/道具图）+ 垫图/参考图 + 局部重绘 + **主模型锁定** + **跨集位置预对齐** + 人工调色 + 动态分镜 | **强**（当事人访谈，有署名、有作品、有平台） | 新华社、央广、环球时报、海报新闻、品玩、36氪、白泽影视 |
| **B. 教程 / 开源工作流层** | 三视图 / 4 View 资产板 / LoRA / ControlNet / IP-Adapter / 固定 seed / 色卡 / 连续性锁 / 判废表 / Asset-First 门禁 | **中**（可执行、可复现，但作者多匿名或化名，且**未证明已被在播项目采用**） | 漫剧老李、seedance-han、drama-skills、ai-drama、塔猴、培训机构 |
| **C. 平台官方层** | 参考图张数上限、主体库、元素标签、素材红线 | **强**（官方文档原文） | 字节 Seed、可灵、Vidu、MiniMax、阿里云百炼、腾讯云 |

**【我的推断】用法上的区别很重要：**
- 要做**产品/工具**，B 层最适合直接抄成字段（它本来就是"可执行规则库"）；
- 要**说服制片团队或甲方**，只有 A 层的话术有说服力；
- 要**判断能力边界**，只有 C 层可信。
- **如果把 B 层术语当作"国内从业者的普遍做法"来陈述，是过度归因**——这是本报告最容易犯的错误，我在正文里已尽量逐条标注。

### 1.5 "资产库"这个词本身

**【业界共识】** 容器叫法不统一，但指同一件事：
- 《**资产图册**》/《剧组资产图册》（漫剧老李，作者自称"工业化台账"）
- **数字资产包**（漫剧老李 P2 阶段名）
- **角色资产库 / 角色参考库**（ArcLoop 手册标题："短剧的角色资产库怎么搭"）
- **Series Bible / 剧集圣经 + Character Bible / 角色圣经**（英文借词在国内被直接使用）
- **主体资产库 / 主体库**（来画 AI 漫剧的正式功能名，也是一个国内厂商对这件事最直白的定义）
- **元素库 / 主体库 / Element Library**（工具侧叫法，见第 2 节）
- **视觉设定.md + 连续性锁**（`drama-skills` 的落地形态）

> **【业界共识 · 厂商文档级】** 来画 AI 漫剧的官方内容页《AI 漫剧角色一致性怎么做？用主体资产库打造长效 IP》（2026-08-20）把这件事讲得最直白，可直接引用：
> - 标题结论句：**"解决办法不是不断加长提示词，而是先把人物变成可以重复调用的资产：AI 漫剧主体库负责固定角色外观，音色库负责保存声音，全能参考模式负责控制镜头中的人物与画风。**先有资产、再做内容**，是 AI 漫剧从单条作品走向 IP 长期运营的关键。"**
> - **三步法**：① 把角色形象存进主体资产库（准备清晰角色设定图，**优先用主体完整、背景简洁、光线均匀的图片**；条件允许补充**正面、侧面、背面**素材；**统一命名**——"一个角色对应一个主体名称，避免'女主''主角''小林'等多个名称同时指向同一人物"；**检查角色/场景/道具分类**——"角色放入角色资产，固定场景与关键道具分别管理，**不要把多个主体塞进同一张参考图**"）；② 创建个人音色完成角色声音绑定（"把声音也作为角色资产保存，而不是每集临时重选"）；③ 用参考图约束跨镜头造型（**"形象参考与风格参考分开准备。固定人物时使用角色设定图，统一画风时使用独立风格样张。不要让一张复杂图片同时承担人物、场景、动作和风格四种任务"**——这与 ArcLoop 的"参考职责拆分"完全同构，是两个独立来源的相互印证）。
> - **连载工作流原话**："系列创作可以按照'**剧本—资产—分镜—合成—复盘**'的顺序推进。工作流稳定后，每集主要更换剧情内容，而不是重建人物。"
> - **一条容易被忽略的产品建议**：FAQ 里明确"**AI 短剧制作新手应该先建资产还是先出片？——先完成一条测试短片，确认角色和画风符合预期，再把满意的角色、声音和场景存入资产库。这样既不会在早期建立大量无效资产，也能为后续连载减少返工。**"→ 即**资产库不是开机前就要建全的，而是"试探片验证通过后沉淀"**。
> - 来源：[content.laihua.com/index.php/case/1480.html](https://content.laihua.com/index.php/case/1480.html)（⚠️ 这是**厂商内容营销页**，规格数字（如"专业模式可扩展到最多 99 个分镜、最长 1000 秒"）**不代表行业口径**；但其中的方法论表述与多个独立来源一致，故可信度较高。）

> **【我的推断】** 叫法分裂的根因：**云端闭源工具管这叫"主体/元素"（平台侧存的是特征向量），本地路线管这叫"参考图/LoRA"（存的是像素与权重），流程派管这叫"资产图册"（存的是图 + 引用关系）。**做产品时不必纠结叫法，要对齐的是"图 + ID + 用途 + 锁状态"这四件东西。

### 2.2 可灵 Kling（快手）

- 有独立的 **Element Library / 元素库（主体库）**，把角色、道具等保存为可复用"元素"，在多镜头间绑定。官方文档页：[Kling Element Library User Guide](https://klingai.com/quickstart/klingai-element-library-3-user-guide)、[主体管理（3.0 omni API）](https://klingai.com/document-api/api/video/3-0-omni/elements)。
- **图生视频界面下 Elements 模式：最多上传 4 张图**，用于构建"一致的角色 / 物体 / 服装 / 环境"（["Frames: 上传一张图让 Kling 动起来 / Elements: 上传最多 4 张图构建一致性场景"](https://pikalabsai.org/kling-ai-elements-swap-objects/)，第三方实测文，2026-01）。该文与腾讯云 API 文档的"1 张正面 + 1~3 张其他"上限**互相印证**。
  - 该文的实测经验（**社区经验，非官方**）：**建议最多 2 个一致角色**，加第三个就开始串；**建议最多 3 个元素**；`prompt` 里必须**逐个提到每个元素**，"只上传不写进提示词"的元素不会出现；支持**在参考图里框选单个元素**（selective picking），以及**用白底图出资产**以提升拾取精度；负面提示词加 `morphing, anatomical errors, glitch` 有效；**单张图上传会被当成普通图生视频，不做角色参考**（即"单主体一致性"这条路走不通）。
  - 格式限制：JPEG / PNG，**单图 ≤10MB**。
- **从官方 API 更新日志可以看到「元素/主体库」这条产品线的完整演进**（来源：[Kling API Updates](https://kling.ai/document-api/updates/api.md)），这条时间线本身就是"资产库"重要性的官方证据：
  - **2025-03-25** 图像生成 V1.5 支持**角色特征参考（Face）与角色外观参考（Subject）**——官方描述："选 Face 可保持脸一致，用 prompt 改服装和背景，**适合单角色跨造型一致性**；选 Subject 可把整个主体作为参考，还能**分别微调脸与主体的参考强度**，适合**跨场景保持角色外观**"
  - **2025-07-30** 图生图 V2.1 支持**主体参考 + 场景参考 + 风格参考**（三类参考同时出现的起点）
  - **2025-10-20** 上线 **Image Element Recognition API**："识别主体、人脸、服装等，每次请求可返回 4 组结果"，明确用于 **Multi-Image to Video 与 Multi-Elements**
  - **2026-01-23** 上线**元素多角度智能补全**："通过元素的正面视图，自动推断该元素的其他角度图像，**每次生成三组结果供选择**；按访问次数计费，每次 0.5 单位"——**平台在帮你自动生产"三视图"**
  - **2026-02-25** 元素能力全面升级：支持**通过视频创建元素**、创建时可**绑定音色**并在生成时指定；创建元素升级为异步服务；新 API `advanced-custom-elements`（**注意：新旧元素库相互独立、不能跨 API 查询**）
  - **2026-03-04** V3.0 Motion Control：**绑定元素可增强元素一致性**，但绑定时**只能参考视频中人物的朝向**
  - **2026-03-23** **多图元素也支持绑定音色**（此前只有视频角色元素支持），通过 `element_voice_id` 传参
  - **2026-04-23** 支持**原生 4K 输出**（`mode=4k`）
  - **2026-05-07** **解除"多镜头"与"首尾帧"的互斥**，多镜头视频也可定义首尾帧（`kling-v3-omni` / `kling-v3`）
  - **2026-06-17** 3.0 Omni 参考视频时长扩展到 **3–15 秒**，支持 **4K**；参考视频作特征参考时支持多镜头生成（`multi_shot=true` + `shot_type=intelligence`）
  - **2026-09-15** 虚拟试穿 V3.0：支持平铺图/模特图/上身图三种服装输入，**支持锁定模特姿态、保持模特面部、选择是否保留原背景**
  - **通用提醒**：Kling 官方公告"**通过 API 生成的图像/视频将在 30 天后自动清除**"（2025-09-29 及更早）——**这直接决定了"资产库必须自己落盘归档"**
- **Kling 3.0 / AI Director 支持"单次多镜头"，最多 6 个机位打进一次生成**（Nomi 调研仓库记录，来源 [kling.ai Director Mode 教程](https://kling.ai/blog/kling-video-3-director-mode-multi-shot-tutorial)）。**"6 机位"为第三方整理口径**；官方 API 文档另有更精确的口径：**多镜头最多 6 个镜头、每镜头 ≥1s、镜头提示词 ≤512 字符**（见下）。
- **Kling 3.0 Omni 的"参考图 / 元素"数量矩阵 —— 这是全篇最硬、也最容易算错的一组官方数字**（[官方 API 文档 Omni Video Generation](https://kling.ai/document-api/api/video/3-0-omni/video-omni)）：

| 场景 | 上限 |
|---|---|
| 首帧或首尾帧生成视频 | 元素 **最多 3 个** |
| 无参考视频 + 仅多图元素 | **参考图 + 多图元素合计 ≤7** |
| 无参考视频 + 仅视频角色元素 | 视频角色元素 **≤3** |
| 无参考视频 + 两者混用 | 视频角色元素 **≤3**，且参考图+多图元素 **合计 ≤4** |
| **有参考视频** + 仅多图元素 | **参考图 + 多图元素合计 ≤4** |
| **有参考视频** + 仅视频角色元素 | 视频角色元素 **≤1** |
| **有参考视频** | **视频角色元素与多图元素不可同时使用** |
| 参考视频 | **最多 1 段**；加参考视频后最多再加 1 个视频角色元素 |

  其它官方硬限制：参考图/首尾帧 `.jpg/.jpeg/.png`、**≤50MB**、宽高 **≥300px**、比例 **1:2.5 ~ 2.5:1**；参考视频 `.mp4/.mov`、**≤200MB**、时长 **3s ~ 15.5s**、边长 700–4553px、总像素 ≤8294400、比例 0.4–2、帧率 24–60fps；提示词 **≤3072 字符**（建议 ≤2500）；输出 720p/1080p/**4K**；时长 3–15s；**元素标记语法 `@xxx`，官方警告避免元素名互为子串（`@Zhang` 与 `@ZhangSan`）**。

### 2.6 腾讯混元 Hunyuan

**（a）混元生视频（云产品）= 聚合层**
- 它把 Kling / Vidu 等第三方能力统一封装（`CreateAigcElement` 创建主体、`SubmitReferenceToVideoViduJob` 提交 Vidu 参考生视频），Provider 字段填 `kling` / `vidu`。来源同上。
- 【我的推断】价值在于提供了一套**跨厂商统一的主体管理 API**（主体 ID + 8 类标签 + 音色绑定 + 参考图/参考视频），这本身就是"资产库"思路的官方化。**混元自研视频模型在云产品里的多图参考上限未查到明确口径。**

**（b）HunyuanCustom（开源自研，2025-05 开源）= 真正的"身份编码"路线**
来源：[快科技《腾讯混元视频生成工具全新开源：人物不会"变脸" 物体不会"漂移"》](https://m.mydrivers.com/newsview/1046512.html)、[腾讯云开发者社区](https://cloud.tencent.cn/developer/article/2519018)
- **核心主张："图像提供身份，文本定义一切"**——通过**身份增强机制 + 多模态融合模块**，"真正实现在保持人物一致的情况下，改变人物所在的环境和动作"。官方原话点出这是"此前视频生成模型都无法实现"的。
- 能力清单：**单主体视频生成**（**一张**目标人物或物体的图片 + 一句文本）、**多主体视频生成**（**一张人物图 + 一张物体图** + 文本）、**单主体视频配音**（人物图 + 音频 → 说话/唱歌/音视频同步表演）、**视频局部编辑**（把图中人物或物体替换/插入到任意视频片段）。
- 官方效果主张："单人、非人物体、多主体交互等多种场景，都能保持身份特征在视频全程的一致性与连贯性。**人物不会'变脸'，物体不会'漂移'。**"
- **额度极小：单主体 = 1 张图；多主体 = 2 张图（1 人物 + 1 物体）。**
- **【我的推断】** 这条对"资产库"的含义很直接：**"身份编码"路线只需要 1 张干净的资产图**——它把"一致性"从"堆参考图"变成了"编码身份"。所以资产图的**质量（干净、正面、白底、无排版污染）远比数量重要**。这也反向解释了为什么 Kling 官方建议"用白底图出资产"。

- **Edit Model（V8.1 / V8.2）＝ 当前推荐路径**（[官方帮助中心](https://docs.midjourney.com/hc/en-us/articles/48495453462797)）：**「Generate new images using up to 4 reference images (replacing Omni Reference and Character Reference)」→ 最多 4 张**；长宽比自动匹配**第一张**上传图；不兼容 `--tile`，结果不兼容 Remix；多角色冲突时官方建议把多个角色合成一张参考图
- **长期主体库：没有。** 可长期复用的只有 **Moodboards（风格）**、**Personalization 档案**、**Style Codes**——**角色一致性靠每次传参考图**。
- **【我的推断 · 但有旁证】** Kling Elements 的第三方实测文里有一句关键对比："Character consistency was possible by training a Flux LoRA or **using character reference on Midjourney**, but **combining a character reference with an object reference is new**"——即 Midjourney 的 `--cref` 传统上**只做角色参考**，把"角色 + 物体"放进同一次参考是多图参考（`--oref` / Kling Elements 这一代）才有的能力。

### 2.8 Gemini / Nano Banana（多图合成）

- **Nano Banana Pro（Gemini 3 Pro Image）官方技术规范**（[Google Cloud 官方文档](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/gemini/3-pro-image?hl=zh-cn)）：

- **未查到官方口径**：「保持 5 个人物一致性」「最多 5 人」这类数字在 Google 官方文档中**不存在**，**不要引用**——Google 只给了"每提示词 14 张图"这一个硬数字。

- 中文圈实测把 Nano Banana（Pro）当成**"关键帧工厂"**用：先用即梦/Nano Banana Pro 把关键帧做出来，再交给 Seedance 2.0 动起来（秋叶 PPT 实测文）。

### 2.9 ComfyUI 本地组合（IPAdapter / Reference-only / ControlNet）

**先纠正三个流传很广的错误说法：**
1. **「Reference-only 有 strength 参数」→ 错。** `ReferenceOnlySimple`（"Reference-only"）**没有 strength 参数**，只有 `batch_size`（默认 1）；且它**不在 ComfyUI 核心**，在 `ComfyUI_experiments` 实验仓库。有 strength 的是核心节点 `unCLIPConditioning`（`strength` 默认 1.0、范围 −10~10；`noise_augmentation` 默认 0）与 `ReferenceLatent`（**也没有 strength**，官方描述"可链式叠加设置多张参考图"）。
2. **「InstantID = IPAdapter + ControlNet OpenPose」→ 错。** InstantID = InstantID 适配器 + **用 5 点人脸关键点（`draw_kps`）专门训练的 IdentityNet ControlNet** + InsightFace antelopev2（512 维 ArcFace）；**仅 SDXL**；**只取画面中最大的人脸**，官方 README 明说「We have not supported multi-person yet」。
3. **「PuLID 官方说 1 张脸图」→ 错。** 作者源码遍历整个 image batch 逐张编码后**取平均**，即支持多张平均。

**各节点在"一致性"里负责的不同层（本地路线最重要的分工认知）：**

| 手段 | 脸/身份 | 服装 | 风格 | 构图 | 姿势 | 关键源码级数字 |
|---|---|---|---|---|---|---|
| **IPAdapter**（standard/plus） | 弱（需 FaceID 变体） | 中 | **强** | **强** | ✗ | `IPAdapterAdvanced.weight` 默认 **1.0**，范围 **−1~5**；`weight_faceidv2` 默认 **1.0**，范围 **−1~5.0**（源码默认回退 `weight×2`） |
| **IPAdapter FaceID / plus-v2** | **强** | 弱 | 弱 | ✗ | ✗ | 需 insightface 且每种必须配自己专属 LoRA |
| **Reference-only / ReferenceLatent** | 弱 | 弱 | 中 | 弱 | ✗ | **无 weight/strength 参数** |
| **ControlNet openpose** | ✗ | ✗ | ✗ | ✗ | **强** | `ControlNetApplyAdvanced.strength` 默认 **1.0**，范围 **0~10**；`start_percent` 0 / `end_percent` 1。**多张串联是官方支持**（`set_previous_controlnet`），无上限声明 |
| **ControlNet depth** | ✗ | 弱 | ✗ | **强** | 中 | Depth Anything `resolution` 默认 512 |

| **InstantID** | **强** | ✗ | 弱 | 中（约 **25%**） | 中（由 5 点 KPS 定） | `ip_weight` 默认 **0.8**（0~3）、`cn_strength` 默认 **0.8**（0~10）；官方量化口径「InstantID 模型影响约 **25%** 的构图，其余由 controlnet 决定」 |
| **角色 LoRA** | **强** | **强** | 中 | 弱 | ✗ | `LoraLoader.strength_model` 默认 **1.0**，范围 **−100~100**（**官方无建议值**）；多 LoRA 串联官方支持 |
| **FLUX Redux** | ✗ | 中 | **强** | 中 | ✗ | 核心 `StyleModelApply.strength` 默认 **1.0**，0~10 |
| **ACE++** | **强**（portrait） | **强**（subject） | 中 | ✗ | ✗ | Portrait LoRA **1 张**参考图；`MAX_SEQ_LEN` 默认 **2048**（范围 2048–8192） |
| **OminiControl** | ✗（官方明说主要做**物体**不做人） | 中 | ✗ | ✗ | ✗ | **1 张**条件图，自动 center-crop 到 **512×512**；官方原文「The model primarily works on objects rather than human subjects currently, due to the absence of human data in training.」→ **做角色一致性基本不适用** |
| **Qwen-Image-Edit 系列** | **强** | **强** | 中 | **强** | 中 | Qwen-Image-Edit **仅 1 张**（官方"Only Support Single Image Input"）；**2509 节点 `TextEncodeQwenImageEditPlus` 硬编码 3 张**（image1/2/3）；2511 新增**多人一致性**；`TextEncodeQwenImage21` Autogrow **最多 16 张**；`resolution` 默认 1024（0 = 保持各参考图自身尺寸） |

- **按维度拼装的正确姿势**：**ControlNet 锁姿势与轮廓 → IPAdapter 锁风格与构图 → FaceID / PuLID / InstantID / LoRA 锁脸**。任何单节点都做不到全维度。
- **训练集张数的官方口径比社区保守得多**：HF diffusers 官方 DreamBooth 示例给的是 **3~5 张**（B-LoRA 单图特例：**1 张 + 1000 步**）；kohya 官方只讲 `num_repeats` 机制，**不规定张数**；社区流传的"角色 LoRA 15–30 张"**未查到官方口径**。
- 参考：`prompt-to-asset` 仓库的 [ControlNet / IPAdapter / reference conditioning 调研笔记](https://github.com/MohamedAbdallah-14/prompt-to-asset/blob/main/docs/research/06-stable-diffusion-flux/6c-controlnet-ipadapter-reference-conditioning.md)
- 【业界共识】本地路线的最大优势是**可以叠加**，云端闭源工具是**单一参考通道**，所以云端更依赖"资产图本身做得好"。
- **【重要提醒】ComfyUI 核心的 `nodes_ace.py` 是 ACE-Step 音频节点，与图像编辑的 ACE++ 无关**——名字撞车，别混。

→ **14 张**（Nano Banana Pro）
→ **15 张**（Vidu Q4 Preview）

**【我的推断】** 这张分层表揭示了一个产品设计事实：**"9 张"并不是行业标准，而是"上一代全能参考"的档位**。做资产库时应该按**最低公分母（可灵单元素 2–4 张 / 混元 2–4 张）**设计"单主体投喂包"，按 9 张设计"整镜投喂包"，把 15/30 张当作进阶能力。**如果按 30 张设计，切到可灵/混元/Vidu 全部超限。**

**三个最容易算错的硬约束（务必记住）**：
1. **可灵 3.0 Omni：「参考图 + 多图元素合计 ≤7」，一旦带参考视频就降到 ≤4**；且**有参考视频时"视频角色元素"与"多图元素"不可同时使用**。
2. **Seedance 2.0/2.5 禁止上传含写实真人脸部的素材**（图片与视频均不可）——真人短剧走不了这条路。
3. **Midjourney `--oref` 只允许 1 张图**，且**不兼容 V6.1 inpaint / Vary Region / Pan / Zoom Out / Fast Mode / `--q 4`**，GPU time 翻倍。

**四个关键修正（推翻我早期的推测性说法）**：
- **海螺 MiniMax S2V-01 官方明示是「单图主体参考架构」，且明确「目前开放对单个人物进行参考，未来将继续开放多人、物体、场景」**——即**不支持场景/道具**，官方称相比 LoRA 方案计算成本降到 1% 以下、无需训练。
- **HunyuanCustom 开源版只有单主体**：官方模型卡的「Multi-Subject Video Customization」**未勾选（未开放）**；「一张人物图 + 一张物体图」是**官方新闻稿的能力描述**，不是已开源的能力。
- **InstantID 不是「IPAdapter + ControlNet OpenPose」**（这是流传很广的错误说法）：它 = InstantID 适配器 + **用 5 点人脸关键点专门训练的 IdentityNet ControlNet** + InsightFace antelopev2；且**仅 SDXL**、**只取最大的人脸**、官方 README 明说「不支持多人」。
- **PuLID 官方没说"1 张脸图"**：源码遍历整个 image batch 逐张编码后**取平均**，即支持多张平均；`ApplyPulidAdvanced` 的 `fidelity` 默认 8、范围 0–32，且**"fidelity 越低越像参考图"**（官方原文）。

**【业界共识】跨平台的可移植额度 ≈ 9 张图（保守取 4 张）。** 这直接推出第 6 节的字段设计约束：**一张资产卡必须能压成"1 张图"，否则必然超限。**

**两条本地路线的通用原则（跨模型都成立）**：
- **「张数上限」与「身份保真度」是两件事。** Nano Banana Pro 只承诺"每提示词 14 张图"这个硬数字，**没有**承诺"最多能保持几个角色一致"；ComfyUI 侧同理——**IPAdapter 擅风格/构图，FaceID/PuLID/InstantID/LoRA 才锁脸，ControlNet 锁姿势与轮廓**，必须按维度拼装。
- **官方对训练集张数的口径比社区保守得多**：HF diffusers 官方 DreamBooth 示例给的是 **3~5 张**（B-LoRA 单图特例：1 张 + 1000 步）；社区流传的"角色 LoRA 15–30 张"**未查到官方口径**。参考：`LoraLoader.strength_model` 源码范围 **−100 ~ 100**，默认 1.0（**官方未给推荐值**）。

## 3. 必备 vs 备选：P0 / P1 / P2 与项目体量的关系

> 分档依据不是我拍脑袋，而是三套独立来源都指向同一组"没它就出不了片"的项。
> 判据来自漫剧老李的**唯一判据**与**资产依赖分级 A0~A3**，以及 ArcLoop 的"参考职责拆分"。

### 3.1 判据先行（这是本报告最该记住的一条）

**【某家私有做法 · 但机制清楚且可复用】** `seedance-han` 的《资产决策》给出**唯一判据**：

> **这个东西需不需要和某个特定实物长得一模一样？**
> **要 → 做图片资产。不要 → 只在提示词文本里描述。**

配套的**精细度三档**（逐元素独立判档，不是整片一个密度）：

| 档 | 写法 | 什么时候用 |
|---|---|---|
| 1 粗描 | "远处是树" | 背景元素，长什么样无所谓 |
| 2 细描 | "什么树、多高、叶子什么状态、风从哪吹向哪" | 有明确要求但不要求和特定实物一致 |
| 3 参考图 | 做资产图 + `@` 引用 | 要求和某个特定实物一模一样 |

以及**依赖分级 A0~A3**（漫剧老李）：

| 级别 | 场景 | 是否强制资产链 |
|---|---|---|
| A0 | 纯文字 / 单镜 / 无角色一致性要求 | **不强制**，文字可直投（禁用 `@` 锚点即不受门禁约束） |
| A1 | 单角色单镜 | 资产**可选**（有更稳） |
| A2 | 跨镜角色/场景一致性 | 启用相关角色/场景资产出图 |
| A3 | 多人 / 多场景 / 连续剧集 / 高一致性 | **完整执行 Asset-First 六阶段（默认档）**；判定不清按 A3 处理（宁全勿缺） |

### 3.2 P0 —— 没它就出不了片

| 资产 | 为什么是 P0 | 出处 |
|---|---|---|
| **角色权威肖像（锁定脸）** | "全行业的 make-or-break 步"；跳过 = 主角脸在集与集之间漂移、约 25% 镜头要重跑 | Nomi 调研仓库汇总；ArcLoop"只用文字保存角色"被列为最大坑 |
| **角色图 + ID 的引用关系** | 分镜必须 `@` 引用 ID 而不是重新描述。ArcLoop："**镜头卡里应该引用 ID，而不是凭记忆把角色重新描述一遍**" | ArcLoop |
| **首帧图（图生视频路径）** | **I2V 而非 T2V 是跨镜头一致性的头号杠杆**，"公认比文生视频稳一个数量级"、"跨 60+ 集不漂" | Nomi 调研仓库 / OpenDrama 口径 |
| **场景资产（至少定场图）** | 跨 2 镜以上/关键重场戏的场景必须出图；不出图 = 背景每镜长不一样 | 漫剧老李出图标准 |
| **风格基准（画风 + 色卡）** | 场景/道具/角色三类资产必须**同画风**；不同画风直接出不了片 | `ai-drama`：角色设定图与场景设定图应画风一致 |
| **画幅 / 平台 / 时长锁定（P0 锁）** | 漫剧老李把"画幅、风格、平台在 P0 一次锁定，全流程沿用"列为铁律，且**"未指定不动笔"** | 漫剧老李 |

### 3.3 P1 —— 想稳定就必须加

| 资产 | 堵什么坑 | 出处 |
|---|---|---|
| **场景多机位版 / 轴线声明** | 越轴导致角色左右互换、"观众对房间的感知立刻崩掉" | ArcLoop 多机位指南 |
| **道具资产图（多形态：前/中/后三张合并成一张）** | "手里的东西中途凭空消失"被标为**最高频穿帮**；多形态只给前后两张则中间形变留给模型脑补 = 穿模 | seedance-han 失败模式表 #2 / 资产决策 |
| **表情表 / 情绪范围** | "只审核了一张精修美图，剧本一要求丑一点的情绪，角色就容易翻车" | ArcLoop |
| **服装变体（look）与服装规则** | 区分"哪些固定不变、哪些可随剧情变、哪些必须建新版" | ArcLoop / `lookSchema` |
| **声音资产（音色锁 / 9 维音色描述）** | "AI 漫剧里，声音一致性就是角色连续性的一部分" | ArcLoop / ai-comic-studio |
| **连续性锁（continuity lock）** | 只锁"不随剧情改变、且观众看得出不一致"的可见事实（固定耳饰、外套颜色）；会变的部分留给状态 | `drama-skills` |
| **色彩锁 / STYLE LOCK** | 触发条件明确：**30s 及以上长片，或片中出现多个场景** | 漫剧老李 |
| **多形态/多角度产品图（正/侧/背/顶）** | "产品片几乎一定会转镜头"，只做正面镜头一转就露馅 | seedance-han 资产决策 |
| **主体/元素库登记** | 可复用的持久主体 ID，避免每次重新上传导致"同一角色不同一次生成的特征漂移" | 平台侧（Kling/Vidu 都有） |

### 3.4 P2 —— 锦上添花

- **LoRA 训练集 / 身份微调**：最稳但最贵，只对**长连载 + 主角**回本。
- **亲缘推导表（T1→T2→T3 骨相继承 40%~60%）**：群像戏有价值，单集短剧是过度设计。
- **场景拼接图（左鸟瞰 + 右四向）**：信息密度高，在 9 图额度下是"高性价比一张"，但小项目可省。
- **FACS 微表情 / AU 配方库**：表演精修，属"精品化"而非"能出片"。
- **情绪张力曲线 / 12 节拍可视化**：编剧侧工具，与一致性无关。
- **顶视图机位调度（CAM1~4）+ S4 复杂空间规则**：漫剧老李自己规定"**S4 复杂战斗/超复杂群像才启用**"，日常走一行式站位声明。

### 3.5 按项目体量的差异

| 项目体量 | 必需（P0） | 建议（P1） | 可省（P2） | 关键差异 |
|---|---|---|---|---|
| **单条口播 / 带货短视频** | 一个出镜形象（可只用数字分身/本人）、一张产品图、一个背景 | 色卡、产品多角度、音色锁 | 三视图、场景母版、轴线 | **不需要"库"**——单镜或少数镜，A0/A1 档；产品图是唯一硬资产 |
| **几分钟单集短剧** | 主角 4 View 资产板、场景母版、核心道具、风格卡、画幅锁 | 表情表、服装变体、轴线、STYLE LOCK | LoRA、亲缘推导、顶视图 | 主角 2~4 人；**对手戏要靠首帧图解决多人同框**（Wan 明确单参考只含单角色） |
| **几十集连续剧 / 漫剧** | 上表全部 + **角色资产表分级（A/B/C）** + **持久主体库/主体 ID** + **跨集连续性锁** | 亲缘推导、音色资产表、单元执行表（U01~Uxx）、版本管理（V1/V2 变体） | — | **版本管理成为必需**：服装/伤势/年龄变化必须建"已审核变体"，不能静默替换 |
| **品牌 TVC** | **产品多角度资产图（正/侧/背/顶）+ 材质光学契约** + 风格锁 + 色卡 | 产品"状态前/中/后"三图、珠宝专项（scintillation、焦散）、布光统一契约 | 角色三视图（产品为主角时） | **产品保真 > 人物保真**；"产品长得不对，需求方一眼否掉"被标为**最贵的一类废片** |

## 4. 工作流顺序：资产锁定发生在哪一步（重点）

### 4.1 业界标准顺序（六阶段）

**【业界共识】** 几乎所有来源都收敛到同一条：
`想法/剧本 → 剧集圣经（世界观+角色+分集节拍）→ **锁角色+场景参考图** → 分镜/镜头表 → 分段生成视频（从锁定参考图做 I2V）→ 配音+剪辑+字幕`

**资产锁定 = 第 3 步，在分镜之前，而且在"生成任何视频之前"。**

### 4.2 最严格的一套：Asset-First 六阶段（漫剧老李）

```text
P0 立项锁定（画幅 / 风格 / 平台 / 时长）
  ↓
P1 剧本五阶门控（前提 → 结构 → 节拍 → 实体 → 专业剧本页）
  ↓
P2 【数字资产包】  ← ★ 资产锁定就在这里
  ├─ 2a 实体提取：从剧本自动提取 角色(CHR)/场景(SCN)/道具(PRP)/声音(AUD)
  ├─ 2b 资产清单：全量编码 + 16 项五官 + 6 项材质 + 亲缘推导表 + 用户确认无遗漏
  ├─ 2c 分批出图：①角色（A/B 级 4 View 资产板）②场景（母版+机位调度版/站位版+拼接图）③道具  每批确认锁定
  └─ 2d 交付《资产图册》：全部附资产参考图 + 短锚点 @名 = 唯一权威事实来源
  ↓
P3 空间调度 + 分镜（每镜引用已锁定 @资产图）
  ↓
P4 投喂生成（每单元 ≤15s，三层解耦提示词）
  ↓
P5 质检（含"画幅/脸型/服装与资产图一致"）
```

配套的**六道门禁**（违反即阻断）——这套门禁是整个调研里最"可操作"的东西：

| 门禁 | 位置 | 规则 |
|---|---|---|
| 1 | P2b → P2c | 资产清单未获用户确认 → **禁止出图** |
| 2 | P2c → P2d | 分批资产图未全部锁定 → **禁止进入分镜** |
| 3 | P3 | 分镜引用的 `@锚点` 无对应已锁定资产图 → **阻断并回补出图** |
| 4 | P4 | 投喂提示词引用未锁定资产 → **阻断** |
| 5 | P5 | 质检发现画幅/脸型/服装与资产图不一致 → **P0 阻断** |
| 6 | P5 | 修改稿未跑「局部验证 → 联动冲突检查 → 全量审核」三步复验 → **阻断交付** |

### 4.3 三层事实：另一套等价的锁定机制（`drama-skills`）

| 层 | 锁什么 | 落地 |
|---|---|---|
| 第一层 | **视觉设定 + 连续性锁** | `视觉设定.md` 拆出 `人物/造型`、`地点/视图`、`道具/状态`；核心区分 **身份**（跨集不变）/ **变体**（身份不变但服装、伤势、时段、天气、开合、持有状态变）/ **连续性锁**（只锁不随剧情改变、观众看得出不一致的事实） |
| 第二层 | **参考图的三种状态** | `IMG-*`（只是提示词，图还没出）/ `PLAN-*`（计划由创作者提供）/ `REF-*`（确实存在且已检查）。**只有 `REF-*` 才能进视频提示词的参考槽** |
| 第三层 | **冻结关键帧 + 视觉依据** | 每镜写 `### 冻结关键帧提示词`（起点那一格能看见的东西）；成稿后**反查**这一格里需要保持一致的人物/地点/道具，逐项写进"视觉依据" |

> **【关键设计】** "**只有 `REF-*` 才能进参考槽**"这条，等于给"资产是否真的就绪"加了一个**状态位**。这是第 6 节字段设计里必须有的字段。

### 4.4 哪些资产必须在分镜之前锁死？

按"不锁会怎样"排序：

**必须在分镜前锁死（否则分镜白写）：**
1. **画幅 / 比例 / 平台 / 模型版本**（P0；漫剧老李："未指定不动笔"）——分镜的取景半径、景别规划全依赖它
2. **画风 / 风格锁 / 色卡**——分镜里每一格的提示词都要拼风格前缀
3. **角色身份（脸 + 体型 + 识别锚点）**——分镜只写"角色在做什么"，不重写长相
4. **角色造型（默认服装）与变体清单**——分镜必须知道这一场用哪套造型
5. **场景的空间结构 + 固定参照物 + 轴线基准**——否则机位规划无意义
6. **道具的形态与材质**——决定分镜里要不要给道具特写镜头

**可以在分镜中并行/之后补：**
- 表情表（按剧本情绪按需出）
- 局部特写（衣纹、佩剑、发簪）
- 关键帧（首帧/尾帧）——**首尾帧是分镜的产物，不是资产库的成员**
- 亲缘推导的 T2/T3 配角

**【我的推断】** 首尾帧严格说不属于"资产库"，而属于"分镜产出物"。资产库的边界应该画在：**跨镜头复用 + 与具体剧情状态无关**这两条上。凡是"只属于某一镜"的图（首帧、尾帧、构图锚），不进资产库，进分镜卡。

### 4.5 一个反例：不按顺序做会怎样

中新网报道的《非妖哉》案例（一人制作、一集 10 天、成本约 1 万元）：创作者自述"传统实拍会有一套固定的程序……但到了 AI 创作，**这些是可以倒着做的**"，他"从已经出现的画面重新判断人物的情绪，甚至去重新修改人物和故事"，第一集"最初用来确定风格的一张图，前后消耗了约 10 万积分"；有一个几秒的镜头**试了四五十次**。

**【我的推断】** 这说明：**倒着做在"一人公司 + 强作者性"的精品路线里可行，但它不是工业化路线**。倒着做的代价是返工（推翻整个剧本、单个镜头 40~50 次）。工业化路线之所以要 Asset-First，本质是**把返工成本从"重做几十个镜头"压缩到"重做一张资产图"**。两条路线不该混着用。

### 4.6 第三条独立路线：本地 SD 路线的 5 步 SOP

塔猴平台上的《拒绝 AI"多动症"！AI 漫剧如何靠"可控 SOP"颠覆传统文娱产能？》（2025-12-25）给了一套**偏本地 Stable Diffusion 生态**的 SOP，是本次调研里唯一把"角色定锚四件套"讲全的来源：

**角色定锚四步**
1. **标准三视图 + 种子值锁定**："一切的一致性始于一张完美的**角色设定图**。在创作初期，**不要直接生成剧情图**，而是先利用 Midjourney 或 SD 生成主角的三视图（正面、侧面、背面）"；拿到满意角色后**记录种子值**——"虽然种子值不能保证 100% 一致，但它锁定了噪点的初始状态，是后续所有生成的**基因锚点**"。
2. **LoRA 模型训练**（进阶核心）："如果是制作长达几十集的连续剧，仅靠提示词是不够的，目前文娱工业界的标准做法是训练专属的 LoRA"；**投喂 15–20 张**同一角色的高质量图片，训练几十 MB 的小模型；加载后"无论你怎么写动作提示词，例如在吃饭、在打架、在哭泣，AI 生成的脸部特征和服装细节都能保持 **90% 以上**的相似度"。
3. **IP-Adapter**（即时控制，轻量路线）："上传一张参考图，告诉 AI：'别管提示词怎么写，脸必须长这样'"，**权重 0.6–0.8**。
4. **InsightFace 换脸修复**（最后一道防线）："即使在大的动态镜头（大笑、回眸）中 AI 还是可能画崩"，用换脸插件把定妆照五官贴回跑偏的图。

**场景固化的三条路**
- **ControlNet 线稿（Canny/Lineart）**：用简笔画或实拍空镜提线稿，"无论怎么重绘，房间的墙角、窗户位置永远固定"（即锁**空间结构**）
- **Depth 深度图**：锁景深关系，"确保主角永远站在前景，背景永远是那张沙发"
- **局部重绘 + 蒙版**："保持背景图层锁死，利用蒙版把主角所在区域涂抹并重新生成"；视频化时用 Runway/Pika 的**运动笔刷**涂抹人物，未涂抹的背景"像三脚架拍摄般保持稳定"——"有效解决了长期存在的**画面闪烁**与**背景液化**难题"
- **3D 辅助工作流（头部团队）**："最硬核的场景一致性方案是'3D 资产 + AI 渲染'"——先在 Blender / UE5 搭粗糙 3D 房间，"截取不同角度的画面作为底图，再配合 ControlNet 进行 AI 渲染"，"无论镜头怎么推拉摇移，场景的空间结构都是物理正确的"

**它的五步 SOP（可直接对照）**：
`① 企划（剧本 → 分镜描述）→ ② 资产阶段·定锚（三视图 + 概念图 + 训练角色 LoRA + 确立美术风格）→ ③ 画面生成（SD + ControlNet + LoRA 批量出分镜，IP-Adapter 保脸）→ ④ 动态化（首尾帧控图生视频）→ ⑤ 后期合成（对口型 + 剪辑）`

**【我的推断】** 这套 SOP 与 Asset-First 六阶段的**唯一实质差异**是：它把"锁"做在**权重层（LoRA）+ 几何层（ControlNet）**，而云端闭源路线只能做在**参考图层**。所以本地路线的资产库需要多两类成员：**LoRA 训练集** 与 **ControlNet 控制图（线稿/深度/OpenPose）**。这两类在云端工具里没有对应物——它们也是用户提问里"除了角色卡还要固定什么"的答案之一。

**它给的一个量化承诺值得记下**：两三个人的 AI 小组，**一周做出一集**高质量漫剧样片；而传统验证一个网文 IP 是否适合改编动画"需要几百万做 Demo"。（**厂商/平台侧口径，非独立评测。**）

### 4.8 第五条来源（最硬的一条）：火山引擎「剧创」官方产线

这是本次调研里**唯一由云厂商在官方文档里明写"全剧资产设定"作为流水线一步**的来源（🟢 官方一手）：
来源：[火山引擎「剧创」产品说明](https://docs.volcengine.com/docs/drama-creation/product-description?lang=zh)

- **官方流水线原话**：**「剧本解析 → 全剧资产设定 → 分镜视频生成 → 成片预览」**
- **官方机制原话**：**「通过全局风格锁定与角色状态持续追踪机制，确保跨分镜、跨场景的视觉连贯性。Agent 在生成前自动校验内容是否达标，不达标则主动拦截。」**
- **官方资产口径**：**「配备专属的团队资产库……角色、场景等素材资产自动沉淀至团队空间，实现组织级复用与资产积累」**
- **【我的推断】** 这两句话很关键，因为它们把创作者社群的两件事**产品化**了：
  ① "**全局风格锁定 + 角色状态持续追踪**" = STYLE LOCK + 连续性锁；
  ② "**生成前自动校验、不达标主动拦截**" = 漫剧老李的"门禁"。
  **也就是说，"资产先于分镜 + 生成前门禁"已经从社群土办法变成了云厂商的官方产品设计。**

### 4.9 一条重要的组织学观察：「锁定」是国内流程里的一个正式动作，有 4 种叫法

| 叫法 | 出处 | 属性 |
|---|---|---|
| **锁死** | "主角的脸必须先'锁死'。用统一的角色参考图+提示词模板建一个角色资产库，正脸、侧脸、45 度、全身各存一套"（[火星时代](https://www.hxsd.com/content/59553/)，⚠️培训机构内容） | 社区口语 |
| **锁定段** | "先写一段逐项写实的『**角色锁定段**』，以后每个镜头都把它拼进 prompt"（[MatsuriMW](https://github.com/MatsuriMW/aigc-skills-and-agents)） | 纯文本路线的做法 |
| **定妆 / 定妆资产** | "**定妆资产规范表**、主体定义模板与**判废表**"；要备"**大头照、全身照、场景空镜、文字标签**"（[腾讯云开发者社区](https://cloud.tencent.com/developer/article/2755047)，⚠️正文被前端拦截，仅摘要可见） | 真人写实短剧侧借用影视圈词 |
| **沉淀至主体库** | "生产过程中验证有效的优质资产，按照标准化规范沉淀至主体库，形成团队专属的**资产壁垒**"（Vidu 白皮书媒体转述） | 工具官方口径 |

**【我的推断】** 这 4 个词对应 4 种技术路线（云端参考图 / 纯文本 / 真人写实 / 平台主体库），产品做字段命名时不必统一叫法，但**必须有一个显式的"锁定"状态位**——因为它是所有路线的共同动作。

### 4.10 广告 / TVC 侧的顺序：锁得更早、更硬，而且锁到了合同层

**🔵 广告导演一手原话（广告门刊出的 TOPic 现场分享整理，作者王煜）**——这是本次调研里关于"锁在什么时候"最锋利的一段：
> 「**前期把所有东西都锁死。人物设定、场景设定、服装、影调、运镜参考**——这些全部用 AI 先跑出来，让客户拍板。**拍了板就不能再动。**」
> 「**AI 的调色空间没有实拍大。前期不定调，后期基本没得救。所以做 AI 创作，前期定调是最最重要的事。**」
> 「如果客户后期要改，**往往得倒回去改图。你直接改视频，只会越改越崩。**因为 AI 是基于你喂给它的东西来跑的，东西变了，它就跑歪了。」
> 「以前的 PPM 会用参考图，现在直接用 AI 生成的**关键帧**——质感、光影、动作方向，全在单帧里定调」「**所见即所得地跟客户对齐想象**」
> 「AI 跑一个镜头的修改，**基本就是一天起**」

**【我的推断】** 这段话给出了"资产锁定点"的**商业理由**，比流程理由更有说服力：**资产锁定的本质是"和甲方签一份视觉契约"**。短剧侧的门禁（"未锁定禁止进分镜"）是工程纪律；广告侧的锁定是**验收基准**——客户在资产图上拍板，后续一切都以资产图为验收标准。

**🟠 开源 TVC 流水线的资产生成顺序（可直接引用）**：
> `① 产品图（最高优先级）→ ② 角色三视图（人物要跟产品交互，需先知道产品长什么样）→ ③ 场景图（相对独立，但色调要跟产品图协调）`
> 四条序列原则：**先产品后场景 / 先产品后品牌世界 / 先多宫格后视频提示词 / End Frame 最后**

**⚠️ 一处真实分歧（值得在产品设计时点出）**：
- `seedance-han` 主张「**资产清单在写提示词之前做，顺序不能反**——先有大纲再定资产，反过来会让手上的图绑架内容」；
- `tvc-director` 说「在**分镜脚本定稿后、出分镜关键帧之前**先生成视觉资产图」。

**【我的推断】两者不矛盾但侧重不同，正确的读法是：**
> **① 「资产清单」（判断要不要做图）在分镜之前 → ② 分镜脚本定稿 → ③ 「资产图」（具体生成）在关键帧之前 → ④ 关键帧 → ⑤ 视频。**

这正好解释了第 4.4 节"哪些必须在分镜前锁死"的边界为什么难画：**"要锁什么"在分镜前定，"锁成什么样"在分镜后定**。这也是 Asset-First 六阶段里 P2 被拆成 `2b 资产清单` + `2c 分批出图` 两个门禁的原因。

**新增一条容易被忽略的前置项**：`tvc-ai-director` 把「横屏/竖屏/横竖都要」放在 brief gate 的**最前端**，理由是「避免系统根据抖音、小红书、B 站等渠道自行猜测画幅」。→ **画幅不是后期决定的事。**

**广告侧独有的两道锁（短剧线没有）**：**修改轮次**与**算力配额**要写进合同——从业者原话："问题是 AI 跑完片子之后，后面一个月全在改"，所以"前期就要把规则谈清楚：**支持多少次修改、多少算力配额**"。

**5.1b 分镜级精细化穿帮（来自一份视觉分镜九宫格的规则集，措辞可直接拿去做校验规则）**——来源：[XiaoLuo AI Drama Skill](https://github.com/zhurui0523/XiaoLuo-AI-Drama-Skill)（🟠社区经验）

**5.1c 提示词/节拍级翻车点（`seedance-han` 失败模式表中我之前未收的条目，机制清楚且可复用）**——来源：[失败模式表](https://github.com/1747793412/seedance-han/blob/main/references/%E5%A4%B1%E8%B4%A5%E6%A8%A1%E5%BC%8F%E8%A1%A8.md)（该表带证据等级标注 ✅生产验证 / 🔬机制推导 / ❓待验证，是本次调研里最专业的翻车点清单）

| 症状 | 归因（机制） | 修法 |
|---|---|---|
| 主体瞬移、动作跳步、相邻两帧位置对不上 | 写成了**事件式**（"她隔着围栏喂羊"），中间帧全靠模型猜 | 拆成**状态流四拍**，补齐"起因"与"连锁" |
| 该连贯处出现硬切 | 用"然后／接着"串事件——**顺序词不传导力** | 换因果连词："因为…于是／被…得／这一下让／跟着／随着" |
| 节拍全乱、动作被压缩变形 | **正文里写了绝对秒数**，模型转去凑时长而不是演动作 | 秒数只写分镜表；正文用相对锚点（随即／半秒后／在同一瞬间） |
| 塞进去的动作模型只演了一半 | 一拍塞了超过一个完整动作（**一次完整动作 ≈1.5s**） | 拆拍或砍动作 |
| 每个物体各动各的、谁也不影响谁（**绿幕感**） | 只写了施力没写受力，或元素之间没声明**接触关系** | 补**三级连锁**：受力方多点位反馈 → 沿接触链的二级传导 → 介质反应（尘/布/毛/草/水/光）→ 声音发生点 |
| 构图乱飘、前后景关系不对 | 只写了世界（空间关系）没写画框（画面关系），等于把机位交给模型自己选 | 补**遮挡关系**——"她的肩膀挡住栏后那只羊的半个身子"是**模型判断深度顺序的最强信号，比"浅景深"三个字有效得多** |
| 大动态镜头节拍崩 | 大动态也去框死了所有关系，物理上演不出来 | **松紧有度**：只锁接触关系与因果链，空间与画面关系放权 |
| 该手持的拍成了稳定器质感 | 手持质感**只给了标签没给参数** | **正向写四件事**：晃动来源／幅度／方向／频次。**且不写"绝不是三脚架或稳定器"**——提到那两个词反而可能反向唤起 |
| 说好无台词却配上了人声当台词 | 模型有把任何人声配成台词的强倾向 | 补"这一声是非语言的纯人类生理反应，不是台词不是说话" |
| 爆发动作被加上了预备动作 | 前摇点位没拦 | 补"没有任何过渡没有任何前摇" |
| 匀速运动、突起突停 | **匀速是机器的签名**（默认滑轨、关键帧插值、AI 默认运动） | 把加减速写进动作 |
| 人物走位/朝向不是想要的 | 没以**镜头为参照系**指定走位方式——两种都合法，**模型随机抽选** | 写明是转身背对还是面朝镜头；镜头自身的响应也写 |
| 台词说的时机不对 | **台词的文本位置就是它的时间位置** | 先说 → 放状态描述之后动作之前；做完再说 → 放动作句后面；边做边说 → 并进动作句 |
| 文本里写的风格没体现，画面完全跟着图走 | **图的权重高于文本**，冲突的那段文本等于白写 | 改图或改文使之一致 |
| 上了图但某张没起作用，或以奇怪方式起作用 | 该素材没在提示词开头 **@ 到**，或 @ 了但没做描述补充 | **每个素材都要 @对应图片 + 描述补充，一个不漏** |
| 每一样都写得很细，结果每一样都不突出 | **整片一个密度**——等于告诉模型"每一样都重要" | 逐元素独立判档（粗描/细描/参考图） |
| 长条后段身份/服装/色调漂移 | 单条越长要维持的状态越久 | **先跑小样验节拍再上全长**；拆条时各条从原始资产开卡 |
| 方向性返工：分镜、资产、抽卡全部作废重来 | 需求没问明白就动笔（用途与投放渠道没定就先聊画面） | 先定约束（拿来做什么/在哪展现/想达成什么）再谈方案 |
| 交付后对方才说"我其实想要 xx" | 用开放式问了"你还有什么要求"——**他不是没要求，是想不起来** | 画面/场景/人物外貌/节奏**逐项点名问** |
| 同一条提示词好镜头复刻不出来 | 没记 seed | 记录 seed、提示词、素材与参数；**但官方明确同 seed 不保证一致**，复现需实测 |
| 提交被判违规 | 版权 IP 字眼 | **不要通过标点或谐音绕过审核** |
| 服装/道具与题材打架（"没人穿高跟鞋打架"） | 基础设定没贴合主题 | 落笔前先过一遍主题一致性 |

**5.1d 素材来源准确性（与传统媒体对比，AI 特有的兜底需求）**：`seedance-han` 明确给出「关卡 D」——**需求方口头描述产品外观时必须复述确认**（"圆柱形、磨砂白瓶身、金色旋盖、正面竖向标签"），因为「问了'产品什么样'，对方答'就是那个瓶子'，我按自己的理解写了」会导致**"最贵的一类废片"**。原话：**"复述是纠错点，提问不是。"**

### 5.3 一条被反复验证的纪律

**【业界共识】** ArcLoop 与漫剧老李都提到同一件事，但说法不同：

> **"让一张参考图什么都管"是常见翻车点**——戏剧感肖像能稳住脸，但它同时会把**光线、机位、服装和背景**都带进来。
> 所以要把职责拆开：**身份参考只管这个人是谁，服装参考只管穿什么，姿势参考只管站位，场景参考只管房间，风格参考只管画面处理，声音轨道只管表演方式。**

漫剧老李的等价表述是**六种锚定角色**：
**视觉锚定（身份）｜色卡锚定（影调）｜首帧锚定（像素级）｜尾帧构图锚定（构图级）｜音色锚定（声纹）｜质感锚定（局部材质）**

**【我的推断】** 这是第 6 节字段设计里"**用途（purpose）字段**"的直接来源。一张资产卡如果不写清"允许控制什么 / 不得控制什么"，它就会污染画面。

## 6. 可复用清单模板：一张"资产卡 / 分镜卡"该有哪些字段

### 6.1 设计原则（先立规矩）

1. **资产卡的主键是"图 + ID"，不是文字。** 【业界共识】"名字+装扮不是资产"、"文字描述只是索引标签"。
2. **一张资产卡必须能压成 1 张图投喂**（因为跨平台额度 ≈ 9 图，4 View 板算 1 张）。
3. **每张参考图必须声明用途与禁止用途**（允许控制 / 不得控制）。
4. **必须有状态位**：`IMG / PLAN / REF` 或"未出图 / 已出图未审 / 已锁定"。
5. **身份与变体分离**：身份跨集不变，变体（服装/伤势/时段/天气/开合/持有）按集或按场切换。
6. **有锁字段**：`locked: boolean` + 变更后作废下游的机制（DO-Video 已有 `assetPromptHash` / `sourceHash` 这种指纹思路）。

### 6.2 资产卡（通用骨架）

| 字段 | 类型 | 说明 | 来源依据 |
|---|---|---|---|
| `id` | string | 稳定、朴素、可读的永久 ID（`CHR-荆恪-正面` / `MAYA_COURIER_V1` / `SCN-山门` / `PRP-打火机`） | 漫剧老李编码规范 / ArcLoop ID 规则 |
| `type` | enum | **人物 / 动物 / 道具 / 服饰 / 场景 / 特效 / 其他**（直接采用腾讯云主体的 8 类标签口径） | 腾讯云 `TagList` |
| `name` | string | 展示名 | 通用 |
| `tier` | enum | A 核心 / B 常驻 / C 群众（C 级允许只用文字降级） | 漫剧老李梯队分级 |
| `refImages` | string[] | **可投喂的资产参考图**（主角 = 1 张 4 View 资产板；配角 = 1 张立绘） | 全部来源 |
| `status` | enum | **未出图 `IMG` / 计划中 `PLAN` / 已就绪且已检查 `REF`** —— 只有 `REF` 能进参考槽 | `drama-skills` |

| `anchors` | string[] | **识别锚点 2–3 个**（红围巾、圆框眼镜）——"一致性的关键" | DO-Video `signature` / ArcLoop |
| `signatureDetail` | array | 细节资产：布料微距肌理、发型流向与碎发高光、纽扣/袖口/配饰特写 | 漫剧老李 Detail Assets |

| `materials` | object | 材质光学行为（防塑料感）：金属各向异性高光 / 皮肤次表面散射 / 布料边缘绒毛 / 玻璃焦散 | seedance-han #19 |
| `voice` | object | Voice ID + 声音年龄感 / 语速 / 音质 / 情绪范围 / 发音备注 / 禁止跑偏点（可存 9 维音色描述） | ArcLoop / ai-comic-studio |

| `sourceHash` / `promptHash` | string | 出图时的风格与外貌指纹；不一致 = 资产过期 | DO-Video 现有机制 |

### 6.3 场景卡

| 字段 | 说明 | 来源 |
|---|---|---|
| `id` / `name` | `SCN-山门` | 漫剧老李 |
| `refImages` | **三件套**：① 场景母版（纯基准图，无人物无标注）② 机位调度版（文戏，含 CAM1~4 占位）/ 战斗站位版（武戏，含 `@主角`/`@反派` + 轴线）③ 场景拼接图（左 2/3 鸟瞰 + 右 1/3 四向） | 漫剧老李 |

| `光线时段` | 日景/夜景 + 光源来源 + 色温 + 主光源方向 | 漫剧老李 |
| `固定参照物` | 门 / 窗 / 桌 / 立柱——空间锚点 | 漫剧老李 §3.2 |
| `主色调` | 色卡 | 漫剧老李 |
| `材质 6 项` | 地面 / 墙面 / 道具等 | 漫剧老李 |
| `轴线基准` | **180° 动作轴线 + 观众视角左右定义** | 漫剧老李 §3.3 |
| `氛围` | 主导环境压力 | 漫剧老李 |
| `outImageStandard` | 出图标准：跨 2 镜以上 / 关键打斗 / 重场戏必须出图；一次性过场可仅文字 | 漫剧老李 |

> ⚠️ **画幅铁律**：漫剧老李规定**所有场景出图（功能图/拼接图/道具板）一律 16:9 横版**，无论成片是 9:16 还是 21:9——理由是"参考图只负责锁空间结构与材质长相，成片构图由投喂词的画幅行与镜行控制"。**【我的推断】** 这条非常适合做成产品默认值：**资产图用横版、成片用竖版**，避免资产被竖屏裁切污染。

### 6.4 本地路线的两类额外资产（云端工具里没有对应物）

**这两类才是"除了人物角色卡，还需要固定什么"在本地路线上最容易被漏掉的答案。**

| 类型 | 字段 | 说明 | 来源 |
|---|---|---|---|
| **LoRA 训练集** | `characterId` / `imageSet`（15~30 张同角色高质量图，**统一光线、统一背景、统一服装**）/ `triggerWord` / `baseModel` / `weightsFile` / `recommendedWeight` / `trainedAt` / `version` | 加载后"吃饭/打架/哭泣都保持 90%+ 相似度"；**关键纪律：训练集本身必须统一光线与背景**，否则模型学到的是光照差异而不是身份 | 塔猴 SOP / 社区 |
| **ControlNet 控制图** | `type`（Canny/Lineart / Depth / OpenPose / Normal / MLSD）/ `controlImage` / `strength` / `绑定对象`（场景 or 姿态） | **线稿/深度锁空间结构**（墙角和窗户位置永远固定、主角永远在前景）；**OpenPose 锁姿态**；注意它**不锁长相** | 塔猴 SOP |
| **Seed 锚点** | `seed` / `model` / `promptHash` | "锁定了噪点的初始状态，是后续所有生成的**基因锚点**"——但**官方明确声明同 seed 不保证一致**（通义万相 API 文档原话） | 塔猴 SOP + Wan 官方 |
| **蒙版 / 局部重绘区** | `maskAssetId` / `backgroundLock: bool` | "保持背景图层锁死，用蒙版把主角区域涂抹并重新生成"——治"画面闪烁"与"背景液化" | 塔猴 SOP |

### 6.6 分镜卡（镜头卡）

**综合三套来源（`drama-skills` 模板、`ai-drama` shot-template、ArcLoop shot card）后，字段并集如下：**

| 字段 | 说明 | 来源 |
|---|---|---|
| `shotId` | `SHOT-001` | 通用 |
| `purpose` | 这镜只做一件事（接近 / 回应 / 离场）；**一个 shot 塞两个动作就拆开** | ArcLoop |
| `globalStyle` | 全局设定：画风 / 基调 / 语言 / 主色 HEX / 听觉关键词（**头部区块全片只写一次**） | `ai-drama` / 漫剧老李 |
| `sceneRef` | `@SCN-xxx`（引用已锁定场景资产，不重写场景） | 全部 |
| `cast` | 本镜**全部在场角色**（含静止配角/听话者）：`{ 角色ID, @参考图, 姿态, 情绪, 年龄, 性别, 声音特征 }`；**画外者明写"不入画"** | 漫剧老李在场声明铁律 / `ai-drama` |
| `shotSize` | 景别（极特写/特写/中近/中景/全景/远景） | `ai-drama` |
| `camera` | 机位几何（高度、距离、在轴线哪一侧）+ **只给一个主要运镜** + 镜头与主体的空间关系 | ArcLoop / 漫剧老李 |
| `axis` | 轴线声明（左 A 右 B · 禁越轴） | 漫剧老李 |
| `blocking` | 站位声明四要素（位置 + 朝向 + 动作 + 具名）；多人时**每人具名** | 漫剧老李 |
| `timechain` | 时间段（0–2s 引入 / 2–5s 核心 / 5–7s 结尾），**绝对秒数只写在这里，不写进投喂正文** | `ai-drama` / seedance-han #5 |
| `firstFrameDesc` | **冻结关键帧**：只写起点那一瞬间能看见的东西 | `drama-skills` |
| `lastFrameDesc` | 收尾关键帧：终点写成**可验收的静态画面描述**，并点名要保留的持续动态 | `drama-skills` |

> **【一条极有价值的工程纪律】** `seedance-director` 项目明确提出：
> **"不会因为 Seedance 2.5 支持更多参考，就把整张联系表（contact sheet）当作可靠的逐格控制"**，也**"不会让每一镜复用整张故事板"**——"每个故事板格有 `start → action → end`、blocking、机位意图和**独立裁切 ID**"，"每一镜必须绑定**自己批准的裁切**"。
> **【我的推断】** 这直接反驳了"分镜九宫格直接投喂就能逐格控制"的朴素想法：**多格图可以用于规划，但逐格控制必须靠"独立裁切出的单格"**。对资产库设计的含义是：**分镜卡要能引用故事板里的"某一格裁切"，而不是引用整张故事板。**（Wan 官方则给了另一半口径：多宫格图可以投喂，但"建议单次仅输入一张多宫格图"，且"无需描述每个宫格"。两者不矛盾——Wan 说的是"投喂一张多宫格做整体叙事"，`seedance-director` 说的是"别指望它做逐格精确控制"。）

| 字段 | 说明 |

### 6.8 三条"不要做"的设计纪律

1. **不要把首帧/尾帧塞进资产库**——它们是分镜产物。【我的推断】
2. **不要让资产卡承载剧情状态**——剧情状态属于"变体"或"连续性锁"，塞进身份字段会让资产爆炸（每个角色 × 每套衣服 × 每个伤势 = 一张卡）。
3. **不要用纯文字资产**——【业界共识】"最大的坑，是只用文字保存角色"、"名字+装扮不是资产"。

## 7. 行业体量参考（用于校准"该做多重"）

### 7.0 ⚠️ 先看这一条：报告必须分两层写，因为「术语」和「在播项目的事实」不是一回事

独立核查得出一条**可能影响整份报告可信度分层**的负面结论：

> **在本次全部检索中，没有任何一部国内在播 AI 短剧/漫剧的剧集主创，公开说过自己用了「三视图 / LoRA / ControlNet / 固定 seed / 色卡资产」这些词。**
> 这些术语**只出现在教程、开源 skill 仓库、工具方教程与培训机构内容**里，**不出现在项目复盘里**。
> 项目复盘里实际出现的是：**"种子图"（人设图 / 场景图 / 道具图）、垫图、局部重绘、参考图、角色信息 + 图片、动态分镜、位置预对齐、统一镜头风格、3D 资产复用**。

**【我的推断】所以本报告的所有结论都应显式分成两层，请勿混用：**

| 层 | 内容 | 证据强度 | 代表来源 |
|---|---|---|---|
| **A. 剧集主创一手层** | 种子图（人设图/场景图/道具图）+ 垫图/参考图 + 局部重绘 + **主模型锁定** + **跨集位置预对齐** + 人工调色 + 动态分镜 | **强**（当事人访谈，有署名、有作品、有平台） | 新华社、央广、环球时报、海报新闻、品玩、36氪 |
| **B. 教程 / 开源工作流层** | 三视图 / 4 View 资产板 / LoRA / ControlNet / IP-Adapter / 固定 seed / 色卡 / 连续性锁 / 判废表 / Asset-First 门禁 | **中**（可执行、可复现，但作者多匿名或化名，且**未证明已被在播项目采用**） | 漫剧老李、seedance-han、drama-skills、ai-drama、塔猴、培训机构 |

**这条分层的实际用法**：如果目标是"造一个工具"，B 层更适合直接抄成字段；如果目标是"说服一个制片团队"，A 层的话术才有说服力。**报告若把 B 层术语当作"国内从业者的普遍做法"来陈述，是过度归因。**

### 7.1c 广告侧的「最小可用资产集」（直接回答"品牌 TVC 要固定哪些内容"）

| 层级 | 资产 | 不做的后果 |
|---|---|---|
| **第 0 层｜不可省** | 需求澄清问卷（用途 / **画幅** / 时长 / 参考片 / 禁用项）+ **影调与画风方向锁定** | "方向错误的沉没成本会随生成速度被放大" |
| **第 1 层｜产品** | **产品多视图（各角度 + 关键细节微距）+ 产品标准描述段 + 品牌色值** | 镜头一转就露馅；产品变形；品牌色漂移 |
| **第 2 层｜人物** | 角色三视图（白底，正/侧/背一张图）+ 每段 ref 引用 | 脸跳、换人、抽卡成本失控 |

### 7.3 一致性主线共识（有主创一手证据的版本 —— 建议以此替代第 4 节的"术语版"表述）

> **大模型产文字设定 → 生成"人设图 / 场景图 / 道具图"作为种子资产 → 甲方/平台确认后锁定主模型 → 抽卡时用垫图 / 参考图与局部重绘收敛 → 跨集分段制作在衔接处预对齐人物位置 → 后期人工精修与调色。**

**其中"跨集位置预对齐"是本次调研里最具体、也最少被提及的一条机制**（白泽影视郑杰艺原话）：
> "制作中大家是分段制作，比如我做第一集，你做第二集，场景可能都已经同步了，但是经常遇到**我这一集的结尾人物是站在场景的左边，第二个人制作的人物可能是在场景的右边**，就需要调整。现在已经形成一种机制，**在衔接的地方，前后制作的成员都会提前把位置定好再去做**，起码大差不差。"

**【我的推断】** 这条对产品设计的含义：**"上一镜尾帧 → 下一镜首帧"之外，还需要一个"跨集/跨人衔接位"的显式约定**（角色在场景中的位置、朝向、持物状态）。这是"分镜卡"里 `blocking` 字段从"单镜属性"升级为"**跨镜契约**"的理由。

**另外两条反证，值得保留在报告里以免结论过头：**
- **调色在国内主创层仍是人工精调，不是固定色卡**（郑杰艺原话）："给大模型一定的提示词，它可能会遵循，也有可能不遵循，每条片子出的色调也会有些差别，**还是需要人工来手动进行精调**。"→ 色卡（B 层术语）在 A 层的对应物是**后期人工调色**。
- **遇到模型短板就换模型**（同一访谈）："前期我们定下来用什么模型，基本上就在这个模型上开始做了，不会有大的变化。可能有时候**碰到模型的短处，我们会借助其他模型进行干涉，补足短板**。"→ 资产库不能假设"单一模型"，**必须支持"同一资产在多个模型上投喂"**。

**【我的推断】** 这组数字对资产库设计有两个直接含义：
1. **抽卡倍率约 15:1**（1700 张图 → 95 张成品分镜图）。资产库的价值就是**把这 15:1 压下去**——资产图一旦锁定，分镜首帧是"一次生成 + 局部修正"而不是十几次抽卡。

3. **算力只占成本的 30%~50%，人工精修占 40%~50%**。→ 想让工具真正降本，**要打的是"人工精修"那一半，而不是"抽卡"那一半**——这正好是资产库 + 门禁能吃到的那部分。

## 8. 政策与合规：2026 年新增的"结构性翻车点"，会改写资产库设计

**【这一节可能是整份报告里时效性最强、最容易被漏掉的部分。】**

平台对"角色资产复用"的监管在 2026 年发生了**方向性反转**——过去"一套人脸模板批量起号"是效率优势，现在被明确判为违规。

**红果短剧《关于规范 AI 剧角色创作的公告》（2026-08-03 零点执行）**，🟡 媒体转述（[流媒体网](https://vv.lmtw.com/mzw/content/detail/id/256831/keyword_id/-1)）：
1. **单部剧集内，男女主及核心配角必须拥有独立五官、神态、体态特征；仅更换发型、服饰、底层人脸模板一致的情况，一律判定违规**
2. **跨剧角色面部相似度超 65% 直接驳回**——平台上线了 **AI 人脸相似度比对系统**
3. **AI 分段生成导致的人物变脸、画面畸形、表情僵硬，均无法通过审核**（即"跑偏"从质量问题升级为**过审问题**）
4. **禁止照搬他人原创角色的妆造、道具、美术设计；严禁使用无授权真人写真、明星肖像、原创插画训练生成角色**；定制虚拟人像需**完整留存书面授权文件**
5. **都市类 AI 短剧额外要求**：配音与角色口型精准同步；**摒弃单一怼脸流水线镜头**；片头标注"AI 辅助制作"；**视频底层嵌入溯源元数据**
6. **题材差异化执行**：都市情感 / 家庭温情 / 都市逆袭三类 AI 仿真人短剧强制执行新标准；玄幻、古风、灵异及手绘漫剧维持原规则
7. **另一条政策变量**：**2026 年 4 月起广电总局明确要求 AI 短剧"先备案后上线"**（🔵 [央广中国之声 / 新浪转载](https://finance.sina.com.cn/jjxw/2026-04-29/doc-inhwcvfk6786056.shtml)）

**【我的推断】对"资产库"数据结构的四条硬性含义：**
- 资产库需要 **跨项目（跨剧）去重能力**：同一张脸/同一个底层模板不能在两部剧里复用——`characterId` 的作用域不能只是单项目，需要 **项目组/账号级的人脸指纹**。
- 资产卡需要 **合规凭证字段**：授权文件、肖像/声音授权范围、素材来源记录（用于应对"无法提供合法授权证明"的下架）。
- 输出侧需要 **溯源元数据 + AI 辅助制作标识**：Vidu / 通义 / 混元的 API 都已有 `meta_data` / `LogoAdd` / `watermark` 这类字段，但平台要求的是**视频底层嵌入**，产品需要在合成阶段处理。
- "**摒弃单一怼脸流水线镜头**"意味着**分镜卡要能表达"我不是纯怼脸流水线"**——这正好回到第 6 节的分镜卡设计：景别、机位、轴线、覆盖策略这些字段从"审美选项"变成了"过审证据"。

参考：红果 2026 Q1 已累计下架违规漫剧 **1718 部**，专项治理核查 **1.5 万部**、处置 **670 部**（新民周刊引红果公告）。

## 10. 给"AI 视频工具"的落地建议（我的推断，非业界共识）
1. **资产库的原子是"图 + ID + 用途 + 状态"，不是一张表单。** 表单字段再多，只要没有"哪张图被允许控制什么"和"这张图是否已就绪"，一致性就守不住。
2. **锁在资产上，不在镜头上。** 资产 `locked` 之后，任何资产改动自动作废引用它的所有镜头（DO-Video 已有 `assetPromptHash` / `sourceHash` 的思路）。
3. **门禁要硬。** 最有价值的两道：①**资产清单未确认不许出图**；②**分镜引用的资产未锁定就阻断**。
4. **默认 16:9 出资产图、按成片画幅出口播/成片**——参考图管结构，成片管构图。
5. **一张卡压成一张图。** 4 View 资产板（左脸特写 + 右无头三视）这种"一张图塞多格"的版式，是应对跨平台 ~9 图上限的关键工程手段。
6. **生成前给"额度闸"。** 把即将执行的镜头逐条摊开（数量 / 用哪张参考 / 参数 / 预计额度），用户点头才跑——这是"烧真额度"类工具公认的标配。
7. **把参考职责做成显式字段，而不是提示词里的自然语言。** `purpose: { may_control: [身份], must_not_control: [光线, 机位, 服装, 背景] }`。
