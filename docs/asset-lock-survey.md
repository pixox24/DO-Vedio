# 一致性资产盘点：一场戏里还需要「锁」什么

调研日期：2026-10
范围：AI 视频（图生视频 / 文生视频 / 静态图 + 剪辑）生产工作流中，除「人物角色卡」之外还需要固定下来的资产；并逐条对照本仓库现状。

> **本文是结论。** 两份证据附件供追溯：
> - `docs/asset-lock-survey-evidence.md` —— 中文产业实践与逐家平台官方额度核实
> - `docs/asset-lock-survey-international.md` —— 通用/国际视角与失败模式清单
>
> 标注约定：**官方** = 厂商文档/公告；**实践** = 真实团队或开源项目的一手经验（含自报数据）；**共识** = 多来源交叉印证；**推断** = 由前述事实推出，无直接来源。
>
> **证据分三层，用法不同**（这一层区分比结论本身更重要）：
> - **A 层 · 剧集主创/制片一手**（新华社实地探访、公开访谈）——**只有这层能说服制片团队**；
> - **B 层 · 教程与开源工作流**（各 skill 仓库、平台教程、社区复盘）——**作者多匿名、未证明被在播项目采用，但字段设计最好抄**；
> - **C 层 · 平台官方文档**——**数字最硬，但只覆盖"平台能做什么"，不覆盖"从业者怎么做"**。
>
> **一条术语上的框架修正**：独立核查发现，**没有任何一部国内在播 AI 短剧的主创公开说过自己用了「三视图 / LoRA / ControlNet / 固定 seed / 色卡资产」**——这些词只活在教程与开源仓库（B 层）里。主创真正说的词是**「种子图」（人设图、场景图、道具图）、垫图、局部重绘、参考图、角色信息+图片、动态分镜、跨集位置预对齐、统一镜头风格、3D 资产复用**。新华社实地探访的原话：**"生成的这些图不是剧集的最终画面，而是'种子'"**。对外沟通请使用 A 层话术，别用 B 层黑话。

## 0. 结论速览

1. **根因是模型无状态。** 每次生成独立运行，模型不保留角色记忆，同提示词换 seed 就可能换人。所以一致性不能靠提示词祈祷，必须**外置成显式资产**。
2. **要「锁」的东西分四类，不是一类**：需要生成参考图的**视觉资产**、只写进提示词正文的**文本锁**、用参数冻结的**配置**，以及最容易被漏掉的**元资产**（台账、版本状态、门禁、seed 快照、命名）。角色卡只是第一类里的第一项。
3. **厂商官方架构已经把资产定为三类库：角色库、道具库、场景库**（火山引擎「剧创」官方文档；可灵 Element 的标签体系里也并列 `o_104 Item` / `o_105 Costume` / `o_106 Scene` / `o_107 Effect`）。**道具与场景不是可选项，是和人物同级的资产类别。**
4. **两个跨「镜头数量」的门槛，比任何单项清单都重要**：
   - 从**单镜**跨到**多镜**，第一个必须新增的**不是三视图**，而是「**场景几何母版 + 反打视角**」和「**剪辑级连续性锁**」；
   - 从**单集**跨到**多集**，第一个必须新增的是「**台账与版本状态**」——此时一致性问题的性质从**技术问题**变成**流程问题**。
5. **不能什么都锁。** 参考图槽位稀缺（见 §5），厂商自己都写着"这些是容量上限，不是让你填满每个槽位"；而锁太多会把每条提示词撑满、挤掉本镜真正要执行的动作。业界的经验值是**一集的锁通常是个位数**。
6. **「锁」不等于「保证一致」。** 即梦官方免责声明的原话：**"References improve the information available to the model. They do not guarantee identical faces, products, sound or motion."** 这套做法的价值是把「哪些必须一致」写成可检查的事实，**让穿帮在出图前可见**。这句话应该照抄进 UI 文案。
7. **本仓库现状**：人物这条线（角色卡 → 定妆 → 身份锚 → 参考图优先级 → 过期传播）已经完整；**场景卡是空壳**——只有 6 个字段、没有任何流水线创建它、没有面板、**场景描述从未进入提示词**，`shot.sceneId` 在生产数据里恒为空。**这正是第 4 条所说的那个门槛没跨过去。**
8. **2026 年新增了一整类结构性约束：合规。** 国内平台已上线 AI 人脸相似度比对，**跨剧角色面部相似度超 65% 直接驳回**，"人物跑偏"从质量问题升级为**过审问题**。资产库因此需要**跨项目去重 + 合规凭证 + 溯源元数据**——详见 §8。

## 1. 为什么要锁：模型无状态，记忆必须外置

### 1.1 传统影视早就有一套等价物（这是全篇最重要的类比）

AI 视频里被"锁定"的东西，本质是把传统影视的下列标准件，**翻译成模型可消费的「参考素材 + 文本事实」**：

| 传统影视 | 锁什么 | AI 视频里的对应物 |
|---|---|---|
| **Show bible / series bible** | 剧集设定、连续性事实（连配角母亲的姓名、食物过敏都进 bible） | 角色卡 / 场景卡 / 世界设定 / 连续性锁 |
| **Lookbook** | 影调、色彩、质地、镜头语言 | 风格卡 + 风格参考图（style ref） |
| **Color script / color keys** | 全片情绪—颜色曲线 | 色彩脚本 / 调色 LUT / moodTweaks |
| **Show LUT** | 现场到后期同一套 look | 全局 colorGrade / 统一 grade |
| **场记（continuity）** | 服装、伤口、持物、开合状态 | **连续性锁 + 状态交接** |
| **声音指导** | 主题动机与角色绑定 | 音色 ID + BGM 主题 |

### 1.2 不良后果的量级（用于说服，不用于承诺）

- 抽卡成本：某精品 AI 短剧团队约 10 人，其中 **7–8 人是"抽卡师"**（DataEye / 36氪 报道）。
- 返工成本：一手实践记录称"第一集没锁形象**返工 6 次**，第二集锁死形象后基本一次过"。
- 抽卡倍率约 **15:1**（1700 张生成图 → 95 张成品分镜图）；重滚率约 **25%**。
- 工业化的价值因此可以被精确表述：**Asset-First 的本质是把返工成本从"重做几十个镜头"压缩到"重做一张资产图"。** 反例是《非妖哉》那种"倒着做"的强作者路线（一人制作、一集 10 天）：可行，但代价是推翻剧本、单个几秒镜头试四五十次——它**不是**工业化路线，两条不该混用。

### 1.3 一致性的三条腿

| 手段 | 作用 | 强度 | 本项目对应 |
|---|---|---|---|
| **文本锁** | 逐字相同的名词短语，写进每条受影响的正文 | 弱但普适 | `anchorText()`（人物身份锚） |
| **参考图** | 把「长什么样」直接喂给模型 | 强，依赖模型能力 | `sheet.portraitAssetId` / `referenceAssetIds` |
| **参数冻结** | seed、画幅、首尾帧、控制图 | 强，但只保证可比性 | `shot.seed` / `firstFrameAssetId` |

两条硬规则（都有官方依据）：

- **参考图与首尾帧是两种互斥的模式。** 即梦官方明确要求"首尾构图要用专门的 first-frame / first-and-last-frame 模式，**不要假设两张普通参考图会自动变成端点**"；Seedance 2.5 官方直连同样注明**严格首尾帧与全模态参考互斥**；Veo 3.1 把 `referenceImages` / `image` / `lastFrame` 分成三类输入。Kling 的总结最好记：**关键帧决定「什么时候变」，参考决定「什么不变」**。
- **一张参考图只放一个清晰主体，并且要声明它控制什么。** 官方口径里最狠的一条来自通义万相：**"参考素材为主体角色时，仅包含单一角色"**；海螺 S2V-01 更极端——**只有 1 张图、只有单个主体、只有人物面部**。这意味着**对手戏不能靠一张图塞两个人，得靠首帧图解决多人同框**。
- 由此推出：**场景定场图必须是「空镜、无人物」**，否则人物被烧进场景图，在同一镜头里与角色卡打架。

### 1.4 一个高价值的失败机制：参考图会"污染"

**"让一张参考图什么都管"是常见翻车点**——一张戏剧感肖像能稳住脸，但它会同时把**光线、机位、服装和背景**都带进来。所以职责必须拆开：

> 身份参考只管这个人是谁，服装参考只管穿什么，姿势参考只管站位，场景参考只管房间，风格参考只管画面处理，声音轨道只管表演方式。

等价的中文表述是**六种锚定角色**：视觉锚定（身份）｜色卡锚定（影调）｜首帧锚定（像素级）｜尾帧构图锚定（构图级）｜音色锚定（声纹）｜质感锚定（局部材质）。

**这条直接对本仓库**：`shot.referenceAssetIds` 是一张**扁平列表**，没有任何用途声明，正好踩在这个翻车点上。

## 2. 完整清单

### A 类 · 需要生成参考图的（视觉资产）

| # | 资产 | 形态（业界惯例） | 层级 | 本项目 |
|---|---|---|---|---|
| A1 | **人物身份母版** | 1 张正面半身高清 + 3/4 侧 + 正侧 + 背面；三视图分工明确：**正面用于所有面部特写，侧面/背面用于转身、背影、牵手等动作镜头** | **P0** | ✅ 完整 |
| A2 | **场景几何母版 + 反打视角** | ① 母版：**只有几何、没有人**的 wide ② **反打视角 plate**（漂移最严重的一角）③ 会入画区域的细节 plate ④ 时段/天气变体 ⑤ 拼接图（鸟瞰 + 四向） | **P0** | ⚠️ 空壳 |
| A3 | **道具 sheet（含 hero prop）** | 占满画面 + **比例锚**（一只手/一条桌沿，否则回来变巨物）；**状态键控**——会变状态的道具是两张 sheet；再加装配图固定相对尺度 | P1；产品/物证 = **P0** | ❌ 无（可借 `kind:"object"`） |
| A4 | **服装 / 造型变体** | 每套造型一张正面全身；换装用"最小改动"（只动衣服，脸型/五官/发型/姿态全锁） | P1；有换装 = **P0** | ✅ 角色卡 `looks` + `lookAssetIds` |
| A5 | **风格参考图（style ref）** | 1–3 张"只表达画风"的图 + 一段固定风格词 | **P0** | ❌ 无（原计划 M1 明确未做） |
| A6 | **表情表 / 动作参考** | 6–12 张：中性、克制微笑、震惊、愤怒、恐惧、悲伤、下定决心 | P1（主角全套） | ✅ `expressionAssetIds` |
| A7 | **首帧 / 尾帧** | 首帧：起点那一格能看见的一切 | i2v = **P0** | △ 字段在，无流程 |
| A8 | **音色参考** | voice_id 或参考音频（克隆：<2 分钟为推理时条件化；**≈30 分钟高质量素材**才是权重微调级） | 有对白且跨镜/跨集 = **P0** | ✅ 全局 `voiceId`（单人旁白等价） |
| A9 | **产品 / 品牌图** | 正 / 侧 / 背 / 顶四向 + 材质光学行为 | 带货/广告 = **P0** | ❌ 无 |

**首帧不属于资产库，是分镜产物。** 资产库的边界应画在**「跨镜头复用 + 与具体剧情状态无关」**这两条上；凡是"只属于某一镜"的图（首帧、尾帧、构图锚）进分镜卡，不进资产库。

**首帧是最高杠杆，但机制和直觉相反**：`i2v` **没有身份通道**——请求会按设计拒绝参考实体，**"谁在首帧里，你就得到谁"**，身份只能烘焙进那一帧。所以"先用文生视频、再靠参考图救脸"是走不通的。

**尾帧有个反模式**：把一张图当尾帧会"把'转动一次'的结果提前"；**真正的尾帧应该从实际生成的视频里截取**。

### B 类 · 只写进提示词正文的（文本锁）

| # | 资产 | 说明 | 层级 | 本项目 |
|---|---|---|---|---|
| B1 | **人物身份锚** | 年龄+性别+发型+识别锚点+当镜造型，逐字相同 | **P0** | ✅ `anchorText()` |
| B2 | **场景锚文本** | 空间布局、固定陈设（**按左右顺序点名门窗家具**）、材质、标志物 | **P0** | ❌ 无 |
| B3 | **连续性锁（continuity lock）** | 显式列出"现在必须保持的可见事实"，逐字带进每条受影响的正文 | **P0** | ❌ 无 |
| B4 | **世界设定** | 年代、地域、科技/建筑水平 | 年代题材 **P0**，否则 P1 | △ 只有角色卡 `era`/`region` |
| B5 | **轴线 / 朝向 / 眼位** | 谁占画面左，摄影机永不越轴；人物朝向、站位、视线、出入口 | 同场多镜 **P0** | ❌ 无（归档计划设计过 `facing`，未实现） |
| B6 | **禁漂移清单（负面词）** | 禁文字、禁水印、禁新增人物、禁改身份、禁改 logo | **P0** | ✅ `GLOBAL_NEGATIVE`（但见 §8 的坑） |
| B7 | **情绪→光影映射** | 同一情绪全片用同一套光 | P1 | ✅ `style.moodTweaks` |

**B3 值得展开**，因为它是业界公认最容易被忽略、又最便宜的一层：

> 同一件毛衣第一镜织的是蓝色、第二镜变成红色，通常不是资产写错了，而是**没有任何一条提示词把颜色带进去**：视觉设定写了、关键帧写了一半、运动提示词以为"参考帧已经交代过"就把重复描述删掉了。

**参考图补不上这一层**——一张角色板只能约束它自己画到的部分；正在编织、只成形一半的毛衣、被手挡住的道具、每镜重新构图的服装细节，都落在身份参考"默认不能控制"的一侧。

另一句同样关键的话：**跨镜穿帮多数不是脸变了**，而是——**服装颜色、伤口位置、手里的东西、湿没湿、门开没开、站在轴线哪一侧**变了。这些在剧情里会变，所以不能锁死在三视图里；又必须在相邻镜头里保持，所以不能每镜随手写。

由此得出资产条目的标准三件套：

```
识别锚点   —— 身份，跨集不变（写给人和模型看的事实）
本集状态   —— 会随剧情变的部分（伤口、湿透、开合、持有）
连续性锁   —— 既要跨镜保持、又不随剧情变的最小名词短语（逐字带走）
```

锁面写法（直接采用业界规范）：**最小可辨识名词短语**，「颜色 + 材质/形制 + 物体」，如 `pale blue chunky knit wool sweater`；不含句号、动作、状态、数量、镜头信息和剧情；一个实体一把锁；同一实体两种造型是两把锁。**锁面不能被改写**——少一个 `stand-collar` 都算漂移。校验时会查三处同一字符串：图片提示词正文、冻结关键帧、视频提示词正文；且**锁面不能被粘在更长的词里**（`pale blue knit` 不被 `pale blue knitwear-print fleece` 满足），**也不能只出现在负面提示词里**——那说的正好是反话。

配套的**状态交接**：**每镜验收后的尾帧与状态交给下一镜**。毛衣越织越长、伤口越撕越大这类"进度型"事实靠状态交接，不靠锁。

### D 类 · 元资产（不是图，但决定能不能规模化）

| 元资产 | 锁什么 | 层级 | 本项目 |
|---|---|---|---|
| **资产图册 / 唯一事实来源** | 全部资产编码 + 参考图 + 索引标签，取代纯文字台账 | 团队>1 或跨集 = **P0** | △ 角色卡即台账，但无图册视图 |
| **版本状态机** | 定妆 / 可用 / 待确认 / 废弃 | 跨集 = **P0** | ❌ 无（只有 `locked` 布尔） |
| **参考图就绪状态位** | `IMG`（只有提示词）/ `PLAN`（计划提供）/ `REF`（确实存在且已检查）——**只有 REF 能进参考槽** | **P0** | △ 有候选/选中的区分，但无显式状态位 |
| **参考图用途与禁止用途** | `may_control` / `must_not_control` | **P0**（见 §1.4） | ❌ 无 |
| **取用范围限定** | 正向"仅取…"+ 负向"不取…"，默认隔离参考图里的排版/边框/水印/原构图 | P1 | ❌ 无 |
| **seed 与参数快照** | 终选图的 seed + 提示词一起存，保证可复现 | P1 | ✅ `assetPromptHash`（seed 在 shot 上） |
| **命名与锚点规范** | 项目前缀 + 短锚点；素材库常按精确文件名去重，通用名会静默选错资产 | 团队>1 = **P0** | ❌ 无（资产用 hash 文件名） |
| **门禁 / 质检清单** | 资产图未全部锁定 → 禁止进入分镜；分镜引用的锚点无对应已锁定资产图 → 阻断并回补 | 跨集 = P1 | ❌ 无（只有提示/过期，不阻断） |
| **反向引用** | 改资产时能定位影响面（被哪些镜使用） | P1 | △ 生成 key 可推导，无 UI |
| **授权与合规** | 真人需活体检测授权；生成媒体嵌不可见水印 | 有真人 = **P0** | ✅ `real` 角色不露正脸策略 |

## 3. 必备 / 备选

### 3.1 判据先行：一条唯一判据 + 一个门槛表

**唯一判据**（比任何清单都好用）：

> **这个东西需不需要和某个特定实物长得一模一样？**
> **要 → 做图片资产。不要 → 只在提示词文本里描述。**

配套**精细度三档**，**逐元素独立判档**，不是整片一个密度：

| 档 | 写法 | 什么时候用 |
|---|---|---|
| 1 粗描 | "远处是树" | 背景元素，长什么样无所谓 |
| 2 细描 | "什么树、多高、叶子什么状态、风从哪吹向哪" | 有明确要求但不要求和特定实物一致 |
| 3 参考图 | 做资产图 + `@` 引用 | 要求和某个特定实物一模一样 |

**上锁门槛**（三条同时成立才值得上锁）：① 出现在 ≥2 个镜头（或 1 镜 + 1 张资产板）；② 观众能直接看出不一致；③ **不随剧情改变**——会变的是状态，**状态不上锁**。

再加一条本项目更关心的：④ 它是不是信息/情绪/交易的承载点（hero 道具、产品、场景氛围）？是 → 即使只出现一次也锁。

### 3.2 P0 必备（不锁必然翻车）

1. 角色身份母版（正脸 + 3/4 + 全身，最好加背面）
2. **复用场景的几何母版 + 反打视角**
3. 风格/影调基准（style ref + 统一 grade）
4. **画幅 / 平台 / 模型版本**（一次锁定，全流程沿用）
5. **连续性锁清单**（服装/伤口/持物/开合状态）
6. **首帧图**（i2v 路径；身份的唯一通道）
7. 画风 + 色卡（场景/道具/角色三类资产必须**同画风**，不同画风直接出不了片）
8. **禁漂移清单**
9. 角色音色 ID（有对白且跨镜/跨集）
10. 资产台账 + 命名规范（团队 >1 人）

### 3.3 P1 强烈建议

hero 道具 sheet（含比例锚、状态键、装配图）｜场景时段/天气变体｜**灯光方案（光位 + 色温 + 光比）**｜镜头语言表（命名机位、景别词汇、180° 轴线）｜尾帧 / FLF2V 端点｜色彩脚本｜表情表｜换装变体表｜字幕与包装样式｜参考图用途标签与就绪状态位｜门禁与反向引用

### 3.4 P2 可选

专属角色 LoRA（见 §8 的反方证据）｜ControlNet 姿态/深度预演、3D 灰模、俯视调度图｜音乐主题动机、音效库｜title card 与片头动画｜跨项目复用库｜跨账号资产重建规范

### 3.5 两个门槛（本文最该被记住的结论）

> **从「单镜」跨到「多镜」，第一个必须新增的不是三视图，而是「场景几何母版 + 反打视角」和「剪辑级连续性锁」。**
> **从「单集」跨到「多集」，第一个必须新增的是「台账与版本状态」——因为此时一致性问题的性质从技术问题变成了流程问题。**

### 3.6 按体量

| 体量 | P0 | 可省 |
|---|---|---|
| 单条口播 / 带货（≤3 镜） | 1 张风格参考 + 首帧图 + 画幅；**卖货则加产品图** | 三视图、场景母版、道具表、台账。**不需要"库"** |
| 几分钟单集（**本项目主场景**） | 角色母版 + **场景几何母版&反打** + hero 道具 + 每镜首帧 + 连续性锁 + 统一调色 | LoRA、亲缘推导、顶视图机位调度 |
| 几十集连续剧 / 漫剧 | 上表全部 + 全量资产库 + 命名与锚点 + **版本状态机** + 音色绑定 + 门禁 + seed 快照 | — |
| 品牌 TVC | 产品四向资产图 + 材质光学契约 + 风格锁 + 色卡 + 包装 | 角色三视图（产品为主角时）。**产品保真 > 人物保真** |

## 4. 时机与顺序

业界顺序（**已有官方产品设计背书**）：火山引擎「剧创」官方文档写明的流水线是 **「剧本解析 → 全剧资产设定 → 分镜视频生成 → 成片预览」**，机制是「**全局风格锁定与角色状态持续追踪**，确保跨分镜、跨场景的视觉连贯性」，且「Agent 在生成前自动校验内容是否达标，**不达标则主动拦截**」，并「配备专属的**团队资产库**，角色、场景等素材资产自动沉淀至团队空间，实现**组织级复用与资产积累**」。

> **这意味着"资产先于分镜 + 生成前门禁"已经从社群土办法变成了云厂商的官方产品设计。** 另有主创一手表述（白泽影视 AI 事业部，20 人 / 60 集）：「剧本立项—AI解析—人设生成—抽卡生视频—后期精修」，且「**当所有设定都明确后**……让模型生成角色的图片……**经平台方确认，就可以开始创作分镜**」。

阿里云百炼的短剧前期流水线把项目目录定成六类资产：`script / roles / casting / storyboard / art / audio`（`art` 就是场景/道具/服装图）。

**一处表面矛盾需要这样读**：有来源说"资产在写提示词之前定、顺序不能反"，也有来源说"分镜脚本定稿后、出关键帧之前生成资产图"。正确的读法是**把"资产"拆成"清单"和"图"两件事**：

```
① 资产清单（判断要不要做图）   ← 在分镜之前
② 分镜脚本定稿
③ 资产图（具体生成）           ← 在关键帧之前
④ 关键帧
⑤ 视频
```

这也解释了为什么严格的 Asset-First 会把"分批出图"做成两道独立门禁。

**「锁定」这个动作在国内有 4 种叫法**：锁死 / 锁定段 / 定妆（配"定妆资产规范表 + 判废表"） / 沉淀至主体库——分别对应 4 种技术路线（云端参考图 / 纯文本 / 真人写实 / 平台主体库）。**产品不必统一叫法，但必须有一个显式的"锁定"状态位。**

**必须在分镜之前锁死**（否则分镜白写）：① 画幅/比例/平台/模型版本 ② 画风/色卡 ③ 角色身份 ④ 角色造型与变体清单 ⑤ **场景空间结构 + 固定参照物 + 轴线基准** ⑥ 道具形态与材质。

**可以在分镜中并行或之后补**：表情表、局部特写、关键帧（首尾帧是分镜产物）、次要配角。

**门禁制**（比"提示"强得多）：资产清单未确认 → 禁止出图；资产图未全部锁定 → 禁止进入分镜；分镜引用的锚点没有对应已锁定资产图 → **阻断并回补出图**。

**一个高性价比的中间结论**：如果只做一件事，就把"环境描述"从 `shot.description` 里提出来，变成场景卡上的、逐字注入的场景锚文本。这一步不需要任何新的生图能力，成本最低，收益最大。

两条与本表配套的官方证词：

- **seed 不能兜底。** Midjourney 官方原话："**Seeds can't capture or bookmark a specific style, character, or appearance across different prompts.**" 这正是把 seed 归到 C9/P2 的依据——它只保证可比性，不保证一致。
- **声音也是身份资产。** OpenAI Sora 官方发布页把 characters 机制描述为：用一次**短视频 + 录音**验证身份并捕获形象，从而得到 "an accurate portrayal of appearance **and voice**"，且 "This capability is very general, and works for any human, animal or object"。它对跨镜头的表述也值得抄成标题句：**"follow intricate instructions spanning multiple shots while accurately persisting world state"**。（Sora 的 web/app 已于 2026-04-26 停服、API 于 2026-09-24 停服，此处只作机制佐证。）

**参考图额度是分层的，不是一个"9 张"**：`1 张`（海螺 S2V-01）→ `2–4 张`（可灵单元素 / 混元单主体）→ `5 张`（万相 r2v）→ `7 张`（Vidu q1）→ `9 张`（Seedance 2.0 图像位 / MiniMax H3）→ `14 张`（Nano Banana Pro）→ `15 张`（Vidu Q4）→ `30 张`（Seedance 2.5）。这直接推出四条设计约束：

1. **按"最低公分母"设计两种投喂包**：**单主体投喂包**要能压到 **2–4 张**（可灵单元素 / 混元单主体的水平）；**整镜投喂包**按 **9 张**设计。**如果按 30 张设计，切到可灵 / 混元 / Vidu 全部超限。**
2. **一张资产卡必须能压成"1 张图"投喂**——这正是"4 View 资产板（正面 + 侧面 + 背面拼成一张）"这类版式存在的工程理由。
3. **一个镜头只挂一张与机位几何匹配的场景 plate**，而不是把所有场景图都塞进去。
4. **超限必须提示，不能静默截断。** 开源工作流的原话：**缺哪张就列出来，不要静默降级。**

**"主体库"是国产工具的分水岭**：**有**可长期保存的主体资产——可灵（Element Library）、Vidu（`subjects` / `server_id`）、腾讯云混元（`ElementId`）；**没有**对等角色库——即梦/Seedance、MiniMax、通义万相、Midjourney（只有风格向 Moodboard）、Gemini。**音色能作为可参考主体被产品化的目前只有 Vidu、可灵 3.0 Omni、Wan 2.7 三家。** → 结论：**资产库不能把"平台主体库"当唯一真相**，自己的名册必须能独立重建。（另有官方公告：某平台 API 生成的图/视频 **30 天后自动清除**——资产必须自己落盘归档。）

### 5.2 画幅铁律

**所有场景出图（母版/拼接图/道具板）一律 16:9 横版**，无论成片是 9:16 还是 21:9——理由是"参考图只负责锁空间结构与材质长相，成片构图由投喂词的画幅行控制"。**资产图用横版、成片用竖版**，避免资产被竖屏裁切污染。本项目已有 `assetVariants` 按画幅分档，正好可以承载这条。

### 5.3 图片格式门槛（以可灵为例，可直接当校验规则）

`.jpg/.jpeg/.png`；单文件有大小上限；**短边 ≥300px**；长宽比 **1:2.5 ~ 2.5:1**；元素视频来源要 3–8 秒、16:9 或 9:16、仅 1 段、**只支持写实人形**。

### 5.4 作用域陷阱

平台实体是**项目与账号作用域**的："把制作搬到另一个账号意味着要在同名下重建整个 cast"。所以**资产名册与命名规范比平台实体更可靠**——把实体当"可重建"而不是"唯一真相"。另：部分平台的 API 生成物会**定期自动清除**，资产库必须自己落盘（本项目 assets 已是本地落盘，这是隐性优势）。命名还要注意**一个 Element 名不能是另一个的子串**（`@Zhang` vs `@ZhangSan`）。

### 5.5 代际门槛（选型时容易踩）

"**首帧 + 元素绑定**"和"**多角色共指（3+）**"是**可灵 3.0 才有的能力，2.6 及更早没有**。所以"用首帧挂参考槽"这条 SOP 不是通用的，选型时必须把"是否支持首帧 × 元素绑定"当硬门槛。

| 2 | **场景描述从未进入提示词**：编译器只有 内容/人物/镜头/风格/情绪 五个槽 | `lib/core/prompt-compiler.ts:79-131` | 场景卡即使被填了也不生效 |
| 3 | **`shot.sceneId` 从不被写入**：分镜 LLM 只输出 `characters` | `lib/prompts.ts:600-612`、`lib/pipeline/stages/storyboard.ts:101-169` | `doc.scenes` 在生产数据里恒为空数组 |
| 4 | **无连续性锁** | 全仓无对应结构 | 服装主色、道具材质、伤口位置每镜重写、必然漂移 |
| 5 | **参考图没有用途标签**：只按优先级排序，不声明每张控制身份/造型/地理/构图/风格中的哪一面 | `lib/core/cast.ts:277-279` | 正好踩在 §1.4 的污染点上 |
| 6 | **参考图静默截断**：`slice(0, 8)`，超出丢弃无提示，也不区分镜头类型 | `lib/core/prompt-compiler.ts:152-157`、`lib/pipeline/stages/shot-generate.ts:82-85` | 加场景/道具图后会悄悄挤掉角色图 |
| 7 | **无道具卡** | `characterKinds` 含 `"object"` 可代用，但无面板、无语义 | 与官方「角色/道具/场景」三库架构不对齐 |
| 8 | **无轴线/朝向** | 归档计划设计过 `position`/`facing`，`shotSchema` 里没有 | 同场多镜跳轴、人脸朝向跳变 |
| 9 | **无状态交接与尾帧出处** | 无跨镜"上一镜结束状态"的传递结构 | 进度型事实无处安放 |
| 10 | **无风格参考图** | 原计划 M1 记录「未实现，放到 M2」，M2 也没做 | 画风只能靠文字描述 |
| 11 | **无场景侧校验** | `castIssues` 只检查人物 | "这个地点出现了 12 次却没有卡"没人提示 |
| 12 | **平台/模型版本未锁** | `settings.modelId` 只是模型 id | 换模型等于换 look，但流程不提示 |
| 13 | **无版本状态机** | 只有 `locked` 布尔 | 定妆/可用/待确认/废弃四态无法表达 |

一条设计上的印证：本仓库已有铁律——**角色卡不写手持道具**（否则"带着手机"会与当镜动作抢手、画出第三只手，见 `lib/core/cast.ts:259-263`）。这条规则恰好证明道具**必须**是独立卡片并按镜头挂载。而且它还有另一半：**道具不写进锚文本，但必须写进当镜描述**——"手里的道具中途凭空消失"被标为**最高频穿帮**（机制：模型对画面元素没有持久化记忆，长时间不被提及的物件会被后续帧"优化"掉）。本仓库的分镜提示词已经写了"这一镜他手里拿什么、正在做什么，都要写进 description"，方向正确。

## 7. 落地建议（最小改动路径）

### 7.1 资产条目统一用三件套

角色卡已经很接近这个结构（`signature` = 识别锚点，`looks` = 造型变体）。把三类资产对齐到同一套语义：`识别锚点` / `本集状态` / `连续性锁`。`连续性锁` 是新增的第三项。

### 7.2 场景卡该有哪些字段

```ts
sceneCardSchema = {
  id, key, name,
  // 识别锚点（B2）：布局、固定陈设（按左右顺序可点名）、材质、标志物
  description, layout, materials, landmarks[],
  era, region,                                    // 世界设定（B4）
  spatialType,                                    // 室内 / 室外
  lighting: { keyDirection, colorTemp, ratio },   // 光位（不是氛围形容词）
  atmosphere,
  axes,                                           // 轴线基准（B5）
  timesOfDay: [{ id, name, note }],               // 日/夜/黄昏 → 每变体一张图
  angles: [{ id, name, note }],                   // 母版 / 反打 / 细节
  sheet: {
    candidates: string[],                         // IMG 状态
    plateAssetId?: string,                        // 母版空镜（无人物，REF 状态）
    reverseAssetId?: string,                      // 反打 plate
    angleAssetIds: Record<string, string>,
    variantAssetIds: Record<string, string>,
    sourceHash?: string,                          // 复刻角色卡的过期机制
  },
  referenceAssetIds: string[],                    // 用户上传堪景照，优先级最高
  locks: [{ face: string, scope: string[] }],      // 连续性锁
  evidence: [{ lineId, text }],
  absent, locked,
}
```

**一条立即能用的纪律**：母版 plate **只承载几何，不要把光和 grade 烤进去**——光和 grade 属于镜头文本；**换一种光照状态就等于换一张 plate**（从同一锚点派生）。

场景锚文本由代码编译（对称 `anchorText()`），**只写不变的空间事实**，不写"这一镜有谁、在做什么"。

### 7.3 三条最小改动

1. **场景与选角在同一次分析里产出**。`cast` 阶段已经全片读一遍文案、按"主角 / ≥2 句 / 跨章节"决定谁建卡；把"反复出现的地点"用同一套阈值规则一起判定即可——不新增阶段，不新增一次大模型调用。产出仍落成四种之一：**新建 / 复用 / 变体 / 未决**。
2. **给编译器加第六个槽「场景」**。改动面实测很小：`CompileDoc` 的 `Pick<ProjectDoc, ...>` 加一个 `"scenes"`，`compilePrompt` 加一个 `scene` 入参与槽位即可；6 个调用点（`components/visual-style-panel.tsx`、`components/studio/storyboard-panel.tsx`、`lib/core/keys.ts`、`lib/pipeline/stages/shot-generate.ts`、`app/api/projects/[id]/shots/generate/route.ts`、单测）都只消费 `.hash` / `.slots` / `.full`，接口不变。加完后会自然进入 `assetPromptHash` → 自动获得"场景描述改了、旧素材过期"的能力。
3. **参考图配额与用途显式化**：给每张参考图一个用途标签（身份/造型/地理/构图/风格）与禁止用途；按镜头类型分配配额（全景/空镜/交代镜 → 场景图优先；人物特写 → 角色图优先；道具特写 → 道具图优先）；**超限时提示而不是静默截断**。

### 7.4 三条性价比最高的执行纪律

1. **母版只读**：每个角色/场景只认一张"母版"，其它图一律从它派生（i2i），**不再文生图**。特别是**反打视角必须从锚点派生**——"同一房间的多个角度如果分别文生图，就是 N 次互不相干的生成，没有任何东西把角度 2 绑到角度 1"。
2. **锚点回写**：设计文档与成品不一致时**以成品为准**，把成品里的细节回写进档案。
3. **一条提示词只改一个变量**，并保留每次的 seed 与提示词——否则判断不出是什么起了作用，也无法回退。

## 8. 政策与合规：2026 年新增的一整类结构性约束

这一节不是"质量建议"，是**过审条件**。

红果短剧《关于规范 AI 剧角色创作的公告》（**2026-08-03 零点执行**）：

- **单部剧集内男女主及核心配角必须拥有独立五官、神态、体态特征**；**仅更换发型、服饰而底层人脸模板一致的情况一律判违规**；
- **跨剧角色面部相似度超过 65% 直接驳回**（平台已上线 AI 人脸相似度比对系统）；
- **AI 分段生成导致的人物变脸、画面畸形、表情僵硬，均无法通过审核**——"跑偏"从**质量问题**升级为**过审问题**；
- 禁止照搬他人原创角色的妆造 / 道具 / 美术设计；定制虚拟人像需**完整留存书面授权文件**；
- 都市类额外要求：**摒弃单一怼脸流水线镜头**；片头标注"AI 辅助制作"；**视频底层嵌入溯源元数据**。
- 另：**2026 年 4 月起，广电总局明确要求 AI 短剧"先备案后上线"**。

**对数据结构的四条硬性含义**：

1. **资产库需要跨项目（跨剧）去重能力**——`characterId` 的作用域不能只是单项目；同一个"人脸模板"批量起号，从效率优势变成了违规项。
2. **资产卡需要合规凭证字段**——授权文件、活体检测记录、真人人像授权状态。
3. **输出侧需要溯源元数据 + AI 标识**（本项目已有 `aiLabel`，但"底层嵌入溯源元数据"是另一件事）。
4. **"摒弃单一怼脸流水线镜头"意味着分镜卡的景别 / 机位 / 轴线 / 覆盖策略从"审美选项"变成了"过审证据"**——这条把 B5（轴线朝向）从 P1 直接推到 P0。

> 说明：以上是国内特定平台的具体规则，分发渠道不同则约束不同；但"**跨剧去重 + 合规凭证 + 溯源**"这三条对任何要规模化分发的资产库都成立。

## 9. 不要做 / 已知的坑 / 不确定性

### 9.1 明确不建议现在做

- **不要为每类资产各建一个面板与阶段**。人物靠"卡 + sheet + 一条 stage + 过期指纹"就跑通了，场景/道具照抄即可；四套并行流程只会变成四份要同步维护的代码。
- **不要给每一条识别锚点都上锁**。经验值是**一集的锁通常是个位数**——锁面太多会把每条提示词撑满，反而挤掉本镜真正要执行的动作。
- **不要为"完整"做齐所有场景方向**。只有当**摄影方向会改变入口、可见地理、光源、遮挡或叙事功能**时，才值得建立一个新的观察视角。
- **不要把首帧/尾帧塞进资产库**——它们是分镜产物。
- **不要让资产卡承载剧情状态**——剧情状态属于"变体"或"连续性锁"，塞进身份字段会让资产爆炸（每个角色 × 每套衣服 × 每个伤势 = 一张卡）。
- **不要用纯文字资产**——"名字+装扮不是资产"。
- **不值得投入 LoRA**。海螺官方给了最有力的反方证据：**"对于主体类的参考问题，图片参考方案的效果上限足够高，甚至可以优于精调的 LoRA 方案……将计算成本降低至百分之一以下。"** 加上本仓库是"一稿一片"的解说视频，不是稳定 IP 的长剧，样本量级不匹配。
- **不要承诺"锁了就一定一致"**。见 §0.6 的官方免责声明。

### 9.2 六个已验证的坑

1. **反向唤起**：写了"禁止 xx"，画面里偏偏出现 xx——**被禁概念的词根留在提示词里就会被当画面词渲染**。⚠️ **本仓库的 `GLOBAL_NEGATIVE` 内联追加写法（「画面中不要出现：文字、字幕、水印、logo…」）正好踩在这个坑上**，建议默认负向只保留必要项，并评估把"文字/字幕"这类词根从正向可见位置移开。
2. **任何承载文字的东西都会自造文字**：服装图案、招牌、道具、包装——每一镜渲染出不同的错字。定规矩：服装一律 plain、no print；画面里不放文字，字幕后期加。
3. **角色实体通常只锁脸，不锁衣服——而且别信平台的承诺。** 一边是平台的宣称：Pika Character Studio 说单张参考图锁「脸 + 头发 + 服装」，Kling 4.0 官方说 "facial features, hairstyle, clothing, and overall appearance remain recognizable"；另一边是真实项目的实测：**11 帧里 9 帧人物对、只有 4 帧服装对**。结论：服装一致性来自在每条提示词里**逐字重复同一个 wardrobe token**，不要指望实体。（另有官方注脚：Midjourney 明确说 seed 也无法跨 prompt 捕获角色或风格。）
4. **道具的两条反直觉规则**：① 每张 sheet 必须有**比例锚**，没锚的物体回来会变成巨物；② **绝不要把必须离开的道具摆成贴着某表面**（一张平贴玻璃的卡片，三次尝试都让引擎在演员手里长出一个复制品，改成离玻璃一臂远就解决了）。
5. **命名必须带项目前缀**（`<piece>_env_window.png`，绝不叫 `window.png`）——素材库常按精确文件名去重，通用名会静默选错资产。
6. **图的权重高于文本，冲突的那段文本等于白写。** 资产图一旦挂上，它控制的东西用文本改不动——**这既是资产库的威力，也是它的风险**：参考图的排版、边框、水印、原构图会被一起搬进画面。所以需要一个**取用范围限定**字段（正向"仅取…" + 负向"不取…"）。同一机制的另一面是"视频模型对否定不敏感、对**词根**敏感"，即上面的反向唤起。

> ⚠️ **反向提醒：不存在 `角色名_正面_01.png` 这类"看起来像业界规范"的命名约定。** 专项检索未找到任何出处；本报告里凡出现具体命名，都标明了来源。同理，请勿把网络流传的"即梦多图参考最多 50 张图"之类数字外推到所有入口——即梦 2.0 官方是 12、2.5 是 50。

### 9.3 不确定性（引用时注意）

- **参考图带来的不一致缓解是概率性的**，不是保证。厂商免责声明已经写明了。
- **部分平台官方页面抓取受限**，少数参数来自第三方实践文档（如 Runway 的 3 图上限、部分 PixVerse 数字——后者官方两个页面自相矛盾，引用时须并列）。
- **"76% 的创作者把一致性列为第一痛点"这类数字来自培训机构博客、无抽样方法**，不要当统计数据引用。
- **VBench 把视频生成质量拆成 16 个维度**（Subject/Background Consistency、Temporal Flickering、Motion Smoothness、Dynamic Degree、Multiple Objects、Human Action、Color、Spatial Relationship、Scene、Appearance/Temporal Style、Overall Consistency…），是"失败模式清单"最中立的骨架，可用来设计验收标准。
- **一个反方观点值得记录**：行业正在用全流程工具自动化中间环节（拆剧本→定角色→生成→剪辑），部分元资产（如逐镜提示词模板）可能被产品吸收；但**资产本身（脸、场景、道具、音色）仍然必须被定义一次**，只是由谁定义、以什么界面定义会变。
- **两条会让方案更保守的证据**：① **调色在国内主创层仍是人工精调，不是固定色卡**（主创原话："给大模型提示词它可能遵循也可能不遵循……还是需要人工来手动进行精调"）→ B 层说的"色卡"在 A 层的对应物是**后期人工调色**；② **遇到模型短板就换模型** → 资产库不能假设单一模型，**必须支持同一资产在多个模型上投喂**（与 §5.1"切模型主体库就失效"是同一条）。

**三处事实勘误（请随报告一起传播）**

1. **《补天》不是独立作品、也不属于抖音**——它是 AI 全流程微短剧《中国神话》的第一集，出品方为央视频 + 总台人工智能工作室，共 6 集。
2. **《兴安岭诡事》出品方不是博纳**——是湖南广电旗下风芒传媒 + 杭州炬核智能（导演丁宽，6 人 / 3 个月 / 11 集）；博纳对应的是《三星堆：未来启示录》。
3. **《霍去病》"3 人 48 小时 5 亿播放"是误传**——导演本人澄清：团队近 20 人、48 小时仅为工作时间、不是 80 集、仅两支几分钟短片。**建议给所有"几人几天"的数字都加上风险提示。**

另有一处**行业级数字冲突应标存疑**：某官媒原文写"一部 120 分钟的漫剧，一个 60 人的团队一两天就能完成"，与所有其他来源严重不一致，疑为笔误。

**四处覆盖缺口（勿过度引用）**：① **国内 4A / 代理商从未公开过 AI TVC 资产规范**——广告侧那套"最小可用资产集"是从平台能力与社区教程反推的，不是行业标准文件；② **B站 / 小红书 / 即刻的一手实操未纳入**（登录墙与动态渲染），这是最大的覆盖缺口；③ **没有任何平台公开过"资产交付格式规范"**——本报告的字段设计是从实践反推的**工程建议，不是任何平台的合规要求**；④ 国内 Logo / 包装文字变形未找到一手复盘。
